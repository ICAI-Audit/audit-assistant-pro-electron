# T-024 GSTIN lookup and bulk validation

- Task ID and title: T-024, Consent-gated GSTIN lookup and spreadsheet validation.
- Request source, owner and date: Explicit user request, 11 November 2026.
- Linked feature IDs and decision IDs: F-023; GSTZen GSTR-1 integration remains F-022. No separate decision ID.
- Current behaviour and code evidence: GST Number Master in `src/pages/AuditTools.tsx` required `gstzenApi.createGstin()` before inserting the client-scoped `client_gstins` row. The displayed GST portal authentication notice implied GST Master depended on that integration. A separate `AddGstinDialog` file is not imported by the active app.
- Intended user outcome: after accepting the exact internet-use statement, fetch name and any taxpayer type returned by the user-specified e-waybill API. Import CSV/XLS/XLSX with `GSTIN` in A1; download a matching CSV template; validate locally and query only unique, structurally/checksum-valid GSTINs. Display invalid rows and review/save fetched details locally.
- In scope and out of scope: GST Number Master single and bulk workflows, local client persistence, the fixed `api.e-waybill.in` endpoint, Electron preload/main IPC, tests and docs. Do not remove GSTZen login/GSTR-1 functionality. Do not send the spreadsheet, names, client ID or taxpayer type to the lookup service.
- Binding constraints and open questions: Consent must be explicit per dialog session. Taxpayer type is derived locally from character 14 using the supplied chart; the observed provider response has no taxpayer-type field. Successful registered response shape, provider terms, request limits and data-retention policy remain to be confirmed.
- Inputs, fields and validation: Single GSTIN or first-sheet column A with A1 header `GSTIN`; uppercase/trim/space normalization; state, structure and checksum checks. Standard PAN-based forms require numeric character 13 per the user's explicit choice (stricter than the chart's alphanumeric range). F/I/N/R/M special layouts use chart-defined character-13 and character-15 values. Invalid rows are reported locally and omitted from external requests. Character 14 maps S→ISD, C→TCS, D→TDS, F→Non Resident, I→UN Bodies, R→Tax Return Preparers, M→Temporary ID; allowed unmapped codes default to Regular Dealer and unsupported codes are rejected.
- Source data and provenance: Fixed HTTPS endpoint `https://api.e-waybill.in/api/gstin/validate`; query contains one normalized GSTIN. Response fields consumed are name and recognized taxpayer-type aliases plus the provider validity flag. Fetch time/provider provenance is not persisted.
- Roles, assignments and permissions: Existing authenticated app session required in main IPC; local inserts remain scoped to the currently selected client and current user. This does not change general role policy.
- States and allowed transitions: Dialog consent starts false and resets on close. Bulk lookup runs sequentially with progress; stop takes effect after the current request. Complete fetched rows can be reviewed and saved to the local client master.
- Tables and migration impact: Uses existing `client_gstins` columns `client_id`, `gstin`, `name`, `taxpayer_type`, and `created_by`. No schema change or migration.
- Read and write path: `AuditTools.tsx` → `window.electronAPI.gstinLookup.fetchDetails` → `electron/preload.cjs` → authenticated `gstin:lookup-details` in `electron/main.cjs` → `electron/gstin-lookup.cjs` → fixed HTTPS API. Spreadsheet parsing is local in `src/lib/gstinSpreadsheet.ts`; persistence uses the existing SQLite client IPC.
- Outputs: Single lookup fills name when provider confirms; taxpayer/registration type is derived from character 14. Bulk review lists invalid rows and per-GSTIN provider results. A CSV template and provider-confirmed rows can be saved as CSV via the Electron file dialog. Completed selected rows are saved in SQLite.
- Error, cancellation, retry and duplicate behaviour: Invalid spreadsheet header, unreadable file and invalid GSTIN rows are reported. A provider `valid:false` result is distinct from local structure/checksum validity, is explained on the single flow, and is not included in the verified CSV. Requests are sequential; network/API errors remain on their row. Duplicate GSTIN rows are skipped locally. Stop prevents later requests after the current request resolves. Save rejects rows missing name/type and skips client duplicates.
- Acceptance scenarios: Reject missing consent and unauthenticated IPC without network calls; reject malformed/checksum-invalid GSTIN before API; verify the character-14 type mapping and special layouts; verify a valid GSTIN goes only to the fixed host; parse CSV/XLS/XLSX with required header; show invalid rows and prove none are sent; download a correctly suffixed template and only provider-confirmed rows; exercise API errors; save/reopen local records and verify client isolation; stop a bulk run and verify no later request occurs.

Electron startup passed on Windows; the GSTIN UI flow and provider response for a known authorized test registration remain to be exercised.
