## 1. Why

Auditors receive client documents as PDFs and scans: confirmations, bank statements, agreements, signed financials. Preparing them for the audit file must not send client data out of the firm. PDF Tools does that work inside VERA, offline, and lets the result go straight into the engagement's Evidence Vault or onto a working paper.

## 2. Behaviour before this change

This section describes `main` as it was when the design was written. Phase 1 replaced the inline PDF Tools code described here, so the defects listed below do not apply to the new screen.

- VERA Tools (`/audit-tools`, `src/pages/AuditTools.tsx`) had a "PDF Tools" tab. Its code was the inline `PDFTools` component, about 700 lines of the 3,925-line page.
- Merge and Split worked, using `pdf-lib` in the renderer. Six cards (Word to PDF, Excel to PDF, Redact PII, OCR, Compress, Watermark) were "Coming Soon" placeholders.
- The only output was a browser download. Nothing could be read from or saved to the Evidence Vault.
- Known defects: files could not be reordered before a merge; an encrypted PDF failed with a raw library error; the `.pdf` suffix was removed case-sensitively; "split every N pages" raised one download per part; closing the dialog left split settings behind.

### Must never happen

- A source file is altered. Every operation produces a new file; a vault record is never overwritten.
- A document, a password, or any part of either leaves the machine. Passwords are never stored or logged.
- A file from one engagement becomes visible or usable after switching to another engagement or user.
- A tool reports success while producing a damaged or silently incomplete file.
- A redacted file still contains the redacted text anywhere inside it.

## 4. The screen

The PDF Tools tab keeps its place in VERA Tools (fifth of six tabs, shortcut Ctrl+5, deep link `?tab=pdf`). The meeting's layout is followed: tools on top, files below, select files and then the action.

**While it loads.** The screen's code loads on first use. If that takes longer than 300 ms, a quiet outline of the toolbar and the drop area appears, with "Loading PDF Tools…" for screen readers; a quick load never shows it. Each phase 2 dialog and run module also loads on first use, as its own part of the build: if a dialog takes longer than 300 ms, its tool button shows a spinner until the dialog opens; a dialog that fails to load closes with "The tool could not be opened" instead of taking the screen down.

**Top: tools**, grouped under Organise, Prepare, Convert and Review (`ToolBar.tsx`, `toolRules.ts`):

- Organise: Merge, Split, Delete pages, Organise pages, Resize or crop pages, Compress.
- Prepare: Page numbers, Watermark, Redact, Bookmarks, Protect.
- Convert: Images to PDF, PDF to images, then PDF to Excel, PDF to Word, Make searchable, each as "· soon".
- Review: "Review · soon".

Each group shows its usable tools first and then its not-yet-usable ones as quiet muted text with no border or icon, for example "PDF to Excel · soon" (**owner decision, 14 November 2026**, accepting the UX audit's proposal as meeting T-022). At 1280 × 720 the toolbar takes three rows. A tool button is enabled only when the current selection suits it; clicking, hovering over or focusing an unavailable tool or destination says why, in its tooltip and in one status line under the toolbar for 6 seconds ("Select at least two files to merge"; with files listed and none ticked, "Tick files in the list to use a tool."). The toolbar is one Tab stop (`role="toolbar"`): Left and Right (or Up and Down) move along it, Home and End go to its ends; keys with Alt, Ctrl or Cmd are left to the application. When a dialog closes and gives the focus back to its tool button, no tooltip opens for that focus, so a tool's reason never pops up over a success message; the reason comes back as soon as the user moves the pointer over the button or presses a key on it.

**Middle: files.** One list of the working files. Each row shows a first-page thumbnail, the name, where it came from (Computer, Evidence Vault or Result), the page count or file type, the size, its badges and a checkbox. Two ways to add:

- **Add from computer**: the file picker or drag and drop. PDFs, and images for Images to PDF: JPG, PNG, TIFF, WebP, BMP and GIF. The empty screen's hint reads "PDF, JPG, PNG, TIFF, WebP, BMP or GIF." A TIFF is converted when it is added (5.7); its row says "Converted from a 3-page TIFF" or "Converted from TIFF".
- **Add from Evidence Vault**: a dialog listing the current engagement's vault files that are PDFs or images, with search by name. Locked and approved files may be used as input, since input is read-only.

Rows can be moved up and down and removed from the list. Removing a row never deletes a vault file. The list order is the starting order of Merge and Images to PDF; those two dialogs show the chosen files "in the order shown below" and can change it (arrows on each row, or Alt+↑ and Alt+↓; each move is read out); the run uses the order shown; the list itself is not changed, and the default name follows the first file.

How the list behaves:

- Files just added are ticked: an adding replaces the selection with the files it brings, so Merge can be pressed at once. Results never count as added.
- Once the list has files, the drop strip gives way to an "Add files" button and an "Add from Evidence Vault" icon button at the start of the list bar; files can be dropped anywhere on the list.
- Rows are compact (36 × 48 px thumbnails) and the page panel is at most 460 px or 55% of the window high, so a 1280 × 720 window shows five rows. Below 1,536 px width the list bar's long words become screen-reader text, so the bar stays on one line.
- Long names keep their end in view ("…final copy v3 revised.pdf"): the middle is cut on screen and the whole name is the hover title and the text read out. The same applies to group rows, dialogs' file chips, the order lists, the page panel and Organise headers and the vault picker.
- Badges are written in the normal text colour on a tinted background. A result that is not saved anywhere is marked "Not saved". The list bar's count ("3 not saved"; "3 results not saved yet" on a wide screen) is a button: on hover, on focus and read out it says "3 results are not saved. They are cleared when the engagement changes or VERA closes; click to save them all.", and a click saves every unsaved result (one result: the Save window; several: the folder window). The list size is shown only above 150 MB, as "List is large: 160 MB of 300 MB".
- Previews: a page drawn once at a size is shown wherever the same page is asked for at that size (the page panel and the Organise pages grid share them); up to 400 previews that are not on screen are kept and let go with PDF Tools and on a change of engagement or user. A box still waiting says "Waiting…", then "Drawing…"; only boxes near the view pulse while they wait (a long file's hundreds of off-screen boxes pulsing slowed every long run, section 9). A preview that fails is tried once more when the renderer is idle; a second failure shows "Preview not drawn" with "Try again".

Badge names: "Not saved", "Saved to computer", "Download started" (section 6), "In Evidence Vault", "Signed", "Signature no longer valid", "May contain traces of removed pages" (5.3), "Protected" (a result of Protect with password, 5.18), "Unlocked" (a source opened with its password), "Restrictions removed" (a source that opened without a password but restricts copying or printing), and "Still carries …" (5.1).

**Page view.** Selecting a file opens a page panel with a thumbnail of every page and its page number, 200 at a time. Tools that work on pages (Split's "Chosen pages", Delete pages, PDF to images, Redact) let the user pick pages by clicking thumbnails as well as by typing a list such as `1-5, 8`; the two stay in step. Where pages are only shown (the main screen; Split's other modes), a single click on a page opens the page viewer and the panel's header says "Click a page to view it larger."; while a tool runs, a click opens nothing and the header line says "Wait for the tool to finish to view pages larger." instead.

When exactly one selected PDF has bookmarks, a "Bookmarks" list sits beside the page panel: the file's bookmarks as a tree, read-only. It reads the bookmarks in a background worker after the thumbnails have started. Choosing a bookmark brings its page's group of 200 into view and marks the page for 1.5 s; a web link or a bookmark that goes to no page says why it shows no page; a file over the reading limits shows the first 10,000 bookmarks with a note; a reading that stops answering for 30 s ends with "Try again". Editing is done with the Bookmarks tool (5.10).

**Results** appear in the same list, marked "Result", and can be selected as input to another tool, so a user can merge, number and compress without saving in between. The destinations of section 6 are offered on the selection bar above the list, for the rows that are ticked. The row shows a badge for each destination it has reached. The message that announces a result offers "Add to Evidence Vault" and "Save to computer" for 10 seconds; they act on the rows that run made, looked up again at the click and only while the list belongs to the same engagement and user.

The list lives in memory only, and belongs to one user in one engagement **(design call)**:

- It survives moving to another VERA Tools tab or another screen and coming back.
- It is emptied when the engagement changes or the user signs out. **From phase 2, when the list holds results that are not saved anywhere, the application asks first** (**owner decision, 15 November 2026**), in its own dialog: "Change engagement anyway?" with "6 results in PDF Tools are not saved and will be removed." ("1 result in PDF Tools is not saved and will be removed." for one) and the buttons Stay and Change engagement; on Log Out the title is "Log out anyway?" and the button Log out. Stay has the focus, so Enter and Escape keep everything. It asks from the header's engagement switch, "View All Engagements", Log Out, the Engagements page and the engagement selector; Stay keeps the engagement, the screen and the list; Change engagement (or Log out) goes ahead and the list is cleared as before. A second change made within about a second, while the list of the engagement just left is still being cleared, is not asked about again: those results go whatever is answered. A native question box was tried first; after it Windows gave typing back to the window only when it lost and regained focus, so the question is the application's own. A result only handed to a download counts as not saved, because its completion cannot be seen. A sign-out forced by the session ending, or a change from another route, clears the list at once without asking. While the PDF Tools screen is open the clearing happens before anything from the new context is shown; while it is closed, a watcher inside the PDF Tools code clears the list within about one second (section 11).
- It is lost when the application closes. No question is asked on closing VERA: that needs a main-process change that interacts with the restart of the automatic update, and was not made (section 12). Nothing is written to localStorage or disk until the user chooses a destination.

### Page viewer (phase 2)

Added by the owner on 14 November 2026 after his hand check of phase 1 ("I was not able to see the documents clearly"). It is one component, used on its own and as the page surface of the Redact review, the Organise pages grid's enlarged view, and the Watermark and Page numbers previews.

**Opening it.**

- An expand icon at the top-right corner of every page thumbnail in the page panel and in tool dialogs, shown on hover and when the thumbnail or the icon has keyboard focus. Its name for screen readers is "View page N larger", its tooltip "View larger".
- A single click, a double-click or Enter on a thumbnail that is not a selection toggle (one viewer at a time). Where a thumbnail toggles a page for Split's "Chosen pages", Delete pages or PDF to images, a click, Enter and Space keep toggling it, and the icon opens the viewer **(design call: one key does one thing)**.
- A "View" button on each file row (named "View" and the file name, tooltip "View the pages larger" or "View the image larger"), which opens at page 1; a single click on a row's thumbnail does the same for the mouse, and the View button stays the keyboard's and screen readers' way. For an image file it shows the image with the same zoom controls and no page controls.
- It works for sources, results, images and unlocked protected files. A result of Protect with password (5.18) is shown from the unprotected copy held in memory, with the line "Preview of the content. The saved file asks for its password."
- While a tool runs the larger view is not offered, and the page and icon say "Wait for the tool to finish to view pages larger." (page panel, Bookmarks page strip, Organise pages grid, Watermark preview).

**The window.** A near-full-window dialog inside the application (16 px from each edge), not a separate operating-system window. The header shows the file name and the page size as the reader sees it ("A4 portrait, 210 × 297 mm"; other sizes in mm). Controls:

- Zoom out and in through 25, 50, 75, 100, 125, 150, 200, 300 and 400%; Fit width (the default on opening); Fit page; Actual size. **100% is actual size: one point of the page is 96/72 CSS pixels** (lead ruling), so an A4 page at "Actual size" is 793.7 × 1,122.5 CSS pixels and fit width in a 1280 × 720 window is about 150%. A zoom step passes over a preset within 5% of the current zoom, so the first Zoom in from 149.85% goes to 200%. Ctrl + mouse wheel and Ctrl + plus or minus zoom; Ctrl + 0 fits the page. These keys zoom the page, never the whole application, wherever the focus is while the viewer is open (a control that cannot be used is marked unavailable and keeps the focus, instead of being disabled and dropping it).
- When zoomed in, the page moves with the scroll bars, the wheel, or by dragging with the mouse (the pointer shows a hand).
- Previous and next page: buttons, PgUp and PgDn, Left and Right arrows when the page fits the width (otherwise the arrows scroll), Home and End for the first and last page.
- **Go to page**: "Page n of N" with a box to type a page number; Enter goes there. A number that is not in the file says why under the box and keeps what was typed, selected, for another try: "There is no page 400. Type a number from 1 to 320." ("Type a page number from 1 to 320." for an empty box; "There is no page 3. This file has one page." for a one-page file). Leaving the box goes to a valid number or puts the current page back.
- Turn view left or right in 90° steps. Its hint says: "Turns the view only. The file is not changed. To rotate pages in the file, use Organise pages."
- "Choose this page" when the viewer was opened from a page panel that chooses pages (Split, Delete pages, PDF to images, Organise pages); it reads "Chosen" once chosen. Opened from Delete pages it reads "Mark for removal" and "Marked for removal". It is the same choice as the thumbnail's, both ways.
- A page on which nothing is drawn shows the quiet caption "Blank page", with nothing to retry; "Try again" belongs to a page that failed to draw.
- Close button and Escape. Focus stays inside the viewer while it is open and goes back to the thumbnail, icon or row that opened it. "Close" is used only here; the tool dialogs say "Cancel". Escape is the viewer's own key, handled before any other layer sees it: it closes the Find box first and the viewer second, whatever has the focus or is shown over the page (a tooltip included); opened from a tool dialog, it closes only the viewer. (Before this, an Escape pressed while a tooltip was appearing could be lost: about 1 press in 70 with the processor slowed six times.)

**Find** (**owner decision, 15 November 2026**). A Find button first in the viewer's controls (tooltip "Find text (Ctrl + F)"), and Ctrl + F while the viewer is open, wherever the focus is, open one search box over the top right of the page (it moves to the bottom right when the current match would sit under it): the field ("Find in this file"), the count, Previous match, Next match and Close search. No options and no list of results. Enter and Shift + Enter go to the next and previous match (an input method that is still composing, for example a Hindi keyboard, keeps its own Enter).

- What matches, as the line under the empty field says ("Capitals, extra spaces and line breaks do not matter. 100000 also finds 1,00,000."): capitals do not matter; any run of spaces or line breaks counts as one space, in the file and in what is typed, but a space is still needed where the file has words apart; a comma between two digits is ignored on both sides, so 1234567, 12,34,567 and 1,234,567 find one another (a comma followed by a space, and every decimal point, are kept); ligatures and full-width digits match their plain forms; invisible characters (soft hyphen, zero-width space and joiners, word joiner) are ignored, so Hindi typed with or without a joiner matches. A match may be part of a longer number or word (5000 also finds 15000).
- Text is searched in the order the file stores it, one page per renderer job through the viewer's own copy of the file, from the page shown outward, only while something is typed. The first match at or after the page shown becomes the current one; Next never skips a page not yet read (it waits for it). The count reads "17+ so far" while pages are still being read, then "3 of 17", or "No matches".
- Every match on the page shown is highlighted, the current one in orange; highlights are placed from the text's own positions with the viewer's page mapping, so they stay on the words at every zoom, page rotation, view turn and crop box. The current match is brought into view and read out ("Match 3 of 17, on page 52.").
- Pages with no text are counted once every page is read: "12 pages are scans or blank, so they cannot be searched." ("This file has no text that can be searched. Its pages are scans or blank."). A page that cannot be read is tried twice, then counted ("2 pages could not be read."). Matching stops at 10,000 matches: "Showing the first 10,000 matches. Type more of what you are looking for."
- The page texts read are kept for the next search, up to about 24 MB (the least recently used let go), and let go when the box closes. The words typed are never logged, recorded or put into a message; closing the box wipes the field and clears what the JavaScript engine keeps of the last match. Image files have no Find. Text selection and copy are not in phase 2.

**Rendering.** Pages are drawn by pdf.js through `pdfRenderer.ts`, at zoom × the screen's pixel ratio, so text is sharp. The drawing is capped by the existing canvas limits (8,192 px a side, 50 megapixels) and by a viewer limit of 16 megapixels a page **(design call)**: an A4 page at 400% is 3,175 × 4,490 px at pixel ratio 1 (14.3 megapixels, under the cap) and 4,762 × 6,735 px at pixel ratio 1.5 (32 megapixels, about 128 MB of memory for one page), so the cap applies at 400% from a pixel ratio of about 1.06 upward (for example on a 125% Windows display). When the cap applies, the drawing is enlarged to fit, and the line "Shown at reduced sharpness at this zoom" appears; nothing is cut off. A new zoom is drawn 150 ms after the last change; until then the previous drawing is stretched. Viewer drawings go before every other drawing, including a tool run's pages and thumbnails, and are cancelled when the page changes or the viewer closes. At most three drawn pages are kept: the current one and the pages either side. The viewer has its own document slot, separate from the thumbnails', and draws into its own opaque canvas; image files are shown as an `<img>`. On closing, every drawing, object URL and the pdf.js document are released.

Measured in the application (scratch production build, machine shared with other work): the first sharp drawing of a 300 dpi scan page took 2.3–3.0 s (meanwhile the page's thumbnail is shown enlarged under "Drawing page…"); memory stayed flat over 50 open-and-close cycles and 30 engagement switches; after the page renderer stops answering, pages come back after about 31–35 s, because all drawing shares one worker. Find read the 320 pages of a ledger in 10–11.4 s and a 500-page file in 13–33 s at 100% CPU; a second search of the same file took 1.2–1.4 s.

**Confidentiality.** The viewer shows only files of the current working list, looked up by id each time it draws. It closes, and releases everything it holds, on a change of engagement or user, and when its file is removed from the list. Find checks after every page it reads that the list is still the one the viewer was opened in. Nothing is written to disk. A message never names the file after such a change.

**Viewer from Organise pages and Watermark.** Opened from the Organise pages grid, the viewer shows the page as it is in the file, not with the rotation planned in the dialog, and numbers pages in file order (11a). Opened from the Watermark or Page numbers preview, it shows every chosen page with the marks drawn as the run will make them.

### Keyboard shortcuts of the application (phase 2)

VERA has its own keyboard shortcuts, all listening on the window: Ctrl or Cmd with a letter goes to another screen (Ctrl+Y My Tasks, Ctrl+D Dashboard, and others), Ctrl or Cmd with a digit and Alt with an arrow switch the VERA Tools tab (which unmounts PDF Tools), Ctrl+B folds the sidebar and Ctrl+/ opens the shortcuts list. Before phase 2, any of them pressed inside an open PDF Tools dialog threw the dialog, and what was typed in it, away. On `main` at `a15b4c3` VERA Tools follows `?tab=` only when it changes, so a tab shortcut now really moves to the other tab; keeping these keys away from an open dialog matters more for that reason.

One shared rule (`src/components/pdf-tools/dialogKeys.ts`) keeps every key pressed with Ctrl or Cmd, and Alt with an arrow, from reaching the application while a PDF Tools layer is open; what the key does by itself (copy, paste, select all, a text box's own undo) is left alone. It is attached to every tool dialog and its Stop question, the Evidence Vault and working-paper forms, the password dialog and the list's remove question (`useDialogKeys.ts`), and the page viewer's own key guard uses the same rule. The Bookmarks dialog has its own guard to the same rule, because its tree uses Alt with an arrow and Ctrl+Z and Ctrl+Y itself. A layer's own keys still work (Organise pages' and the Merge and Images to PDF order lists' Alt with an arrow; Ctrl+Z; the viewer's zoom keys and Ctrl+F). The shared tool frame also handles an Escape that no layer took (one that arrived while a tooltip was appearing) as the top layer would have: the Stop question closes, or else the dialog closes, or asks first while a run is going. After a confirmed Stop the frame leaves the focus to the closing question, which puts it on Run (or on the tool's button when the dialog closes).

Checked in the application with keys sent from the main process, from several focus positions in Merge, Split, Compress, Watermark, Organise pages, Protect, the vault form, the Bookmarks dialog and the viewer, with a control step proving that the same keys act when nothing is open. Not covered: Electron's own menu keys (Ctrl+R reloads the window and Ctrl+W closes it) still act while a dialog or the viewer is open; this is application-wide (section 12). The Redact dialog has its own frame but uses the same key guard, the Stop focus rule and the lost-Escape handling; its own keys are zoom, undo and delete. After Escape during its Stop question it stays open, so a review is never lost, where the shared tool frame closes.

## 5. The tools

### 5.1 Rules common to all tools

- A file is checked when added: a PDF must parse and have at least one page; an image must decode. Otherwise it is rejected with the file name in the message; a damaged or half-downloaded PDF adds "It may be damaged or incomplete: download it again, or ask the sender for a fresh copy."
- **Password-protected PDFs.** When a protected file is added, the user is asked for its password. A wrong password can be retried or the file skipped. Once opened, the file works in every tool, and its row is tagged "Unlocked" ("Opened with its password. The copy in this list has no password.").
  - The password is held in memory for that file only, and is never stored, logged or written to the activity log.
  - A result made from a protected file is **not** password-protected. The tool dialog says so before the run ("Statement.pdf was password-protected. The result will not have a password."). The result itself is never described as protected and carries no protection tag; its record says "; protection removed" (flag `protectionRemoved`). Protect with password (5.18) makes protected copies; its result is marked "Protected".
  - A file that opens without a password but carries its author's restrictions (no copying, no printing; this includes a file protected only by an owner password) is opened with the notice "It restricts things such as copying or printing. The copy in this list has no restrictions; use it only if you are entitled to." Its row is tagged "Restrictions removed", and tool dialogs say "… has restrictions (for example on copying or printing). The result will not have them." The original file is unchanged.
- If a source contains a digital signature, the user is warned before the operation that the result will not carry a valid signature: "Keep the signed original as the evidence; use this copy only where a signature is not needed." The operation is still allowed. A signed input is marked "Signed". Every result made from a signed source, whichever tool made it, and every later result made from such a result, is marked "Signature no longer valid" (hint: "Made from a signed file. The signature in this copy is no longer valid. The original signed file is unchanged."). The mark is cautious: a part of a split file that holds no signature is marked too. The activity record carries the flag `signatureInvalid` and the note "; signature no longer valid".
- **Running.** While a tool runs, progress is shown and the run can be stopped. Before a run the dialog's second button is "Cancel"; during a run it is "Stop". Stop always asks first, so that one key press does not lose minutes of work: the question is titled with the tool's name ("Stop Compress?"), says "Compress is still running. If you stop now, nothing is added to the list." and offers "Keep running" and "Stop". After 10 seconds the progress line also shows how long the run has taken ("18 s", "2 min 26 s"). How far a Stop reaches into a run is given in each tool's section; reading a very large file and writing the result are single steps that a Stop waits for. A failure or a stop leaves the list as it was and produces no result row. A failed run says "The tool could not finish, and nothing was added. Open the file in a PDF reader, save a fresh copy and add that." A refusal at Run ends with "Nothing was added."
- **Pace.** Every reading and writing of a PDF by the tools other than Redact gives the window a turn at least every 50 ms of work (`pace.ts`): pdf-lib's own waits, and those of the second library used by Protect and for passwords, are taken by the clock instead of every 1,500 objects, and the tools' loops over pages, files and objects give a turn too; so the screen keeps painting and Stop is seen, and the bytes written are the same as without it (section 8). Split, Delete pages, Merge, Organise pages, Watermark, Page numbers, Resize or crop pages and Bookmarks also see Stop while a file is still being read (within about 50 ms of work); the other tools finish their read first. The checks made on every file added that read its bytes (a signature's byte range, a trailer, an `/Encrypt` entry) go through the file once, giving the window a turn every 4 MB. A file with more than 10,000 `/Encrypt` names, or whose page tree loops or is deeper than 1,024 levels, is refused when added, as damaged; of a file's XMP metadata and a comment's rich text only the first 4 MB are read.
- **What a result still carries.** Every PDF result is counted from its own bytes for what it still carries besides its pages: comments that hold text (not links, form fields, pop-ups or printing marks), attachments (the document's list and file-attachment comments), and which of title, author, subject and keywords are filled in. When it carries any of these, the run message and the row say so in one neutral sentence: "This copy still carries 2 comments, 1 attachment and its title, author, subject and keywords." (several results: "These 10 copies still carry their title and author."; row label "Still carries …"; group row "Still carry …"). Nothing is said when there is nothing. The record keeps the counts (`carried`) and the clause "Still in the file: 2 comments, 1 attachment, title and author.", never a value. Text that only looks hidden (white text, for example) is not looked for and is not claimed either way (11a). This one sentence was chosen as the way to tell the user (**owner decision, 15 November 2026**).
- **Document properties.** Merge, Split, Delete pages, Compress, Images to PDF, the PDF made from a TIFF, Organise pages when pages move or are removed, and Redact set both Producer and Creator to "ICAI VERA". Page numbers, Watermark, Bookmarks, Resize or crop pages and Organise pages when pages are only rotated set Producer and the modification date and keep the source's Creator; Compress keeps its own designed rule above. Protect with password sets neither, because the protected copy must match the source object by object (5.18). A result of Split or Delete pages keeps the source's title, author, subject, keywords and creation date; a merged file keeps none.
- A result of 10 MB or more is announced with "Checking the result…" before it is opened again for the page count, because that opening holds the window for a moment (about 2.5 s for a 41 MB result).
- Default result names are suggested and editable (section 6 covers the rules).

### 5.2 Merge (phase 1)

Combines two or more selected files into one file, in the order shown in the dialog (the list's order to start with; it can be changed there, section 4). Images in the selection are included as pages. Default name: `<first file name>_merged.pdf`, following the first file of the order shown until a name is typed. Stop takes effect between steps: the step in progress finishes, and then nothing is added.

What is not carried over: form fields, links between pages of the source files, and attachments. The dialog says so, naming the files, only when a chosen file has them (for form fields: "Filled-in form fields are not carried into the merged file; the values may not be shown"; for attachments: "Attachments are not carried into the merged file."). The result's activity record is flagged "form fields not carried" or "; some bookmarks not carried". A merged result of 5 MB or more adds one sentence: "Merging does not make files smaller; Compress can make scans smaller."

Bookmarks, from phase 2:

- **Add a bookmark for each file** (on by default): one bookmark per source, titled with the file's name without its extension (an image's too), pointing at its first page, in the order of the merge.
- **Keep each file's own bookmarks under it** (on by default): a source's bookmarks are carried, with their nesting, under its file bookmark, by the rules of 5.10 ("Carried by other tools"). A file bookmark with bookmarks under it starts closed **(design call: a long merged bundle opens with one line per file)**. The option is greyed while the first is off, so "keep each file's own bookmarks" alone is not offered on screen, although the run supports it **(lead ruling: keep the design)**.

Per-file bookmarks are always written and count towards the 10,000 limit; each source's own bookmarks are carried whole, in the order of the merge, while the total stays within 10,000 bookmarks and 32 levels; a source that does not fit is left out and counted, and later smaller sources are still tried. With both options off, no bookmarks are written, as in phase 1; the note then reads "Bookmarks are not carried into the merged file." `bookmarksDropped` and the note "; some bookmarks not carried" mean that at least one bookmark of the sources is not in the result. The record keeps both choices.

### 5.3 Split (phase 1)

Works on exactly one file. Four choices on screen (the first three from phase 1, named in the UX wording pass; file names and records unchanged):

- **One range of pages**: from page A to page B, giving one file. Default name `<name>_pages_A-B.pdf`.
- **Equal parts**: consecutive parts of N pages, giving several files named `<name>_part_01.pdf`, `_part_02.pdf` and so on. Progress reads "Splitting… part n of N" and Stop takes effect between pages, and while the file is still being read within a moment.
- **Chosen pages**: thumbnails clicked or a list such as `1-5, 8, 10-12`, giving one file with those pages in the order written. A page listed twice is included twice **(design call)**.
- **At bookmarks** (phase 2, below), shown only when the file has bookmarks.

PDF to images also says "Chosen pages".

Validation: page numbers are whole numbers from 1 to the page count; a range's start is not after its end; N is at least 1 and less than the page count. Invalid input is explained next to the field in the page list's own words (for example `"32-1" is backwards: the first page must not be after the last`, `Page 400 is outside this file's 320 pages`) and the tool does not run.

**Several files in one run (phase 2, owner decision 15 November 2026).** Ledgers, bank bundles and annual reports are split by section, so Split can make several files at once, and stays as before for one file.

- **A separate file for each range.** Under "Chosen pages", a tick box "A separate file for each range" (off by default: one file with the chosen pages, as before). Ticked, each comma item of the list makes its own file: "1-32, 65-96" gives two files of 32 pages. A page may be in two ranges (both files hold it); a range typed twice makes two files. While it is ticked the thumbnails show which pages are in some file and a click shows the page larger; the hint says "Type each range, separated by commas, for example 1-32, 65-96. Clicking a page below only shows it larger."
- **At bookmarks** ("One file for each main bookmark."): one file for each main bookmark, from its page to the page before the next one's, in page order (not outline order). The pages before the first bookmark go into the first file, so every page is in exactly one file **(design call)**. A main bookmark with no page of its own starts at the first page a bookmark under it opens **(design call)**; one that opens no page of the file (a web address, another file) makes no file; of two at the same page, the first in the outline names the file. A file whose bookmarks cannot be used shows the choice greyed, with the reason in one sentence: "This file has too many bookmarks to read, so it cannot be split at them." (more than 10,000 bookmarks or 32 levels), "This file's bookmarks do not open any of its pages, so it cannot be split at them." or "The bookmarks could not be read, so this file cannot be split at them." The thumbnails mark where each file starts.

Before the run the dialog lists what will be made, "This makes 2 files:", each file's name and pages ("pages 1–32"), five at first and the rest behind "Show all 12 files"; Run reads "Split into 2 files". Anything worth knowing is one short sentence that never blocks the run: "Pages 33–64 are in no file.", "Pages 20–32 are in more than one file.", "Pages 1–2 come before the first bookmark and go into the first file.", "One bookmark opens the same page as another, so it gets no file of its own.", "One bookmark opens no page in this file, so it gets no file."

Names come from one field, "Name the files from" (the file's name by default, cleaned as every name is, at most 90 characters): `<name>_pages_1-32.pdf` for a range and `<name>_page_5.pdf` for one page, as One range of pages names its result; `<name>_01_<bookmark title>.pdf` at bookmarks, numbered in page order (three digits from 100 files), so that a folder lists them in the document's order and two bookmarks with one title get two names **(design call)**. A title is cleaned as a file name, other scripts such as Hindi are kept, an empty title reads "Untitled", and a long title is cut to keep the name within 120 characters, never between a letter and its vowel sign or virama. A range typed twice gets " (2)".

At most 500 files in one run **(design call: each is a row of the list, a name in the vault form and a file in a folder save)**: "These ranges would make 612 files; Split makes at most 500 at a time." The list's room is checked before anything is made and as each file is made: "The files would take the list over 300 MB. Nothing was added; make fewer files or remove some from the list." Progress reads "Splitting… part n of N" and moves with the pages; Stop (asked first) takes effect between pages; nothing is added unless every file was made and checked. The files of one run are grouped in the list as one group row.

Each file carries what Split carries (below): the resources its pages use, its pages' form fields, links to pages of the same file (a link to another file's page is dropped), the bookmarks of its pages, and the source's title, author, subject, keywords and creation date. Each file is the same, byte for byte, as One range of pages makes from those pages. A bookmark of a page in another file belongs to that file and is not counted as lost; one of a page in no file, like one that goes to no page, is counted once, on the first file, which is flagged `bookmarksDropped`. Each file has its own record: "Split pages 1-32 (part 1 of 2)" (options `mode: ranges`, `pages`, `part`, `parts`, `ranges` as typed) or "Split at bookmarks, pages 13-40 (part 2 of 5)" (`mode: bookmarks`, `pages`, `part`, `parts`); a bookmark's title is never in the record, only in the file's name.

**What Split and Delete pages carry** (section 5.4 as well). Split and Delete pages copy only what the kept pages use, so the left-out pages' content, comments, annotations, form values, and the images, drawings and layers that only they use are not copied (tested on generated files covering shared and inherited resources, nested forms, patterns, soft masks, Type 3 fonts, layers, comments with replies and signature fields). **This is not redaction.** Fonts shared with kept pages and the form's default resources are copied whole, a resource whose name a kept page happens to contain is kept, a few non-standard structures are copied as they are, and when a page cannot be read with certainty its resources are kept whole. Do not use Split or Delete pages to remove sensitive content from a file; use Redact (5.9).

Each kept page is given only the resources (images, fonts, graphics settings, colour spaces, patterns) that its drawing may use. When a page cannot be read with certainty, for example an unsupported stream filter, a stream that is not a stream, a resource of an unexpected kind, a non-standard resource key, a name the PDF library does not read exactly, references nested deeper than 32, or an unknown layer setting, its resources are kept whole and the result is marked. The row shows the tag "May contain traces of removed pages" (hint: "Some pages could not be read with certainty, so everything they could draw with was kept. The file may still contain images or fonts from pages that were removed."), a warning message says "Some pages could not be read with certainty. The file may still contain images or fonts from pages that were left out.", the activity summary ends "; may still contain images or fonts of left-out pages", and the record carries the flag `sharedResourcesKept`.

Carried: the form fields that sit on the kept pages, with their values and stored appearances (and the settings that make a viewer draw a field that has no stored appearance); a field keeps only its parts on kept pages, and a field only on removed pages is dropped. Layers are carried with their default visibility. Links to kept pages keep working. Bookmarks that point at kept pages are carried, by the rules of 5.10 ("Carried by other tools"); a bookmark whose own page is left out is dropped and the bookmarks under it move up (lead ruling, 5.10); the dialog says "Bookmarks of pages that are left out are not carried." when the file has bookmarks, and `bookmarksDropped` is set only when at least one bookmark was not carried. Dropped: signature fields as form fields (their visible mark stays on the page); links to left-out pages, including links that go by name to a named destination on a left-out page (a name the source cannot resolve is kept as it is; names of kept pages are not carried, so such links may not work); article threads; structure destinations; a reply's link to a comment that was on a removed page (the reply stays as its own comment), popups whose parent was on a removed page, and links to a missing popup. When the file has attachments the dialogs say "Attachments in the document's list are not carried." (Split and Delete pages build a new document and do not copy them.)

Two of these rules fix phase 1 defects and reach `main` with phase 2 (section 11): phase 1 kept links that went by name to a named destination on a left-out page, and read popup, reply and parent entries in a way that missed a stored null, so a popup could stay on a kept page holding a left-out comment's text.

Measurements, single runs: in phase 1, a generated 300-page scan of 1.85 MB with one image shared by many pages gave 6,088 bytes for one extracted page (1,259,177 bytes before the per-page resources were added) and 1.3 s and 1.8 MB in total for Split every page (57 s and 378 MB before); deleting one page of a 2,000-page generated file took 5.3 s with a peak of 263 MB of memory (15.3 s and 1,370 MB before); a 30-page scan in the application, Delete pages 2 to 30, gave 41,106 bytes holding only page 1's image. In phase 2, in the application on a 320-page, 4.6 MB ledger with an embedded font, at 100% CPU: ten ranges of 32 pages took 21.6 s and Equal parts of 32 took 7.9 s (section 9); each file holds the embedded font, so the ten files take 9.2 MB in all.

### 5.4 Delete pages (phase 1)

Works on exactly one file. The user marks pages on the thumbnails or types a list; the result is the file without them, in original order. Default name `<name>_pages_removed.pdf`. Removing every page is refused. Progress reads "Taking out the pages (n of N)…" or "Copying the remaining pages (n of N)…" and Stop takes effect between pages. Form fields, bookmarks, links, attachments and signature fields are handled as described in section 5.3.

### 5.5 Compress (phase 1)

Works on one or more files, each giving its own result. Four choices: three levels and, from phase 2, "Fit to a size".

| Level (on screen) | What the card says | Image resolution limit | Image quality |
| --- | --- | --- | --- |
| Light: best quality | "Images stay sharp. For documents that will be printed or read closely." | 200 dpi | JPEG quality 0.82 |
| Balanced (default, marked Recommended) | "Images a little softer. For the audit file; clear on screen." | 150 dpi | JPEG quality 0.68 |
| Strong: smallest file | "Images softer and smallest. For emailing; small text in scans may become hard to read." | 96 dpi | JPEG quality 0.45 |

The levels were named Low compression, Recommended and Extreme in phase 1; the values are unchanged. The dialog's note says "Only the images inside are made smaller. Text, fonts and line drawings are not touched and stay sharp. The original file is not changed." No resolution or quality figure is shown on screen. Records use the level names: "Compressed, Balanced (…)".

How it works **(design call)**: images inside the file are reduced to the level's resolution and re-encoded. Resolution is worked out as if each image filled its page, which is exact for scans and errs towards keeping more detail for small images set within a page; the file is then re-saved in a compact structure. Text, fonts and line drawings are not touched, so text stays selectable and sharp at every level. The quality figures are those built into `src/lib/pdf-tools/compress.ts`. Image orientation data is not applied when an image is re-encoded, so pages do not turn. Compress and its Stop work image by image.

**Images with a colour profile (phase 2).** Images in plain RGB or grey, and from phase 2 also 8-bit JPEG and Flate images in an ICC colour space with 3 or 1 components, CalRGB and CalGray, are recoded. An RGB-type image keeps its colour space and profile exactly (the stored numbers are kept, so its colours are unchanged within JPEG tolerance; checked by rendering with the application's pdf.js, which applies profiles). A grey image with a profile that comes back from the browser's encoder with three components is written as plain RGB, so the grey profile is then not applied (11a). Left as they are: CMYK (with a profile or not), Lab, palette images, Separation, DeviceN and images with masks. A 20-page 300 dpi scan of 59.4 MB whose images carry an sRGB profile now gives 13.4 / 4.4 / 1.8 MB at Light / Balanced / Strong; before this fix it gave "Already compact" at every level.

Rules:

- An image is replaced only if its new encoding is under 90% of the old size. Black-and-white fax-style scan images are already compact and are left as they are.
- The result shows original size, new size and percentage saved. When the usual sizes would read the same ("1.0 MB → 1.0 MB"), they are given in whole KB, and failing that in bytes ("1% smaller: 1,043 KB → 1,031 KB").
- If a level gives a file less than 1% smaller, no result is produced, and the message says why: with images a level can still reduce, "Light would not make this file smaller. A stronger level may still make it smaller." (never after Strong); with no images, "No images to reduce" ("This file has no images to reduce, so no level can make it smaller; nothing was added."); with images of a kind Compress leaves alone, "Its images cannot be reduced" ("Its images are of a kind Compress cannot reduce, so no level can make it smaller; nothing was added.").
- Acceptance check: a 20-page colour scan at 300 dpi must come out at least 50% smaller at Balanced with body text still readable at 100% zoom, and each level must be smaller than the one above it.

**Fit to a size (phase 2, owner decision 15 November 2026).** A fourth choice beside the three levels, for portals that cap upload size: "For a size limit, such as a portal's: the best quality that fits, without going below readable." The default view is unchanged (the three levels, Balanced chosen). "Fit to a size" shows four quick picks, **1 MB, 2 MB, 5 MB and 10 MB**, and one box (in MB; "500 KB" typed in it is read as KB; 10 KB to 1,000 MB). The pick offered first is the largest under the file. Run says "Compress to fit 5 MB" ("Compress 3 files to fit 5 MB"). The dialog promises no size before the run: "How small a file can go depends on its images; that is known only by trying."

- Sizes are counted strictly, 1 MB = 1,000,000 bytes, so a result "under 5 MB" also passes a portal that counts 1 MB as 1,048,576 bytes **(design call)**. Sizes are shown in the application's 1,024s, so a result under 5 MB can show as 4.7 MB; a result that does not fit but would read as fitting is said as "just over 5 MB".
- The run reuses the levels' image decisions and searches a 15-step ladder from 300 dpi at quality 0.85 down to a **floor of 72 dpi at JPEG quality 0.36**; Light, Balanced and Strong are steps of it, so a result at a level's step is that level's result byte for byte. The file is re-saved once first: if that alone fits, the images are left as they are; if even removing every image could not reach the size, only the floor is tried. Otherwise four passes at most, each stoppable between images; the progress says "Attempt 2 of 4: reducing images (12 of 40)…". Images are never enlarged, never replaced by something larger, and text, fonts and drawings are not touched.
- **The floor (design call, from a visual check):** at 72 dpi, 10 pt text and amounts in a scan are soft but readable at 100%; at 60 dpi they are misread. The search never goes under the floor. A result at the Strong level's quality or lower says "small text may be hard to read".
- **Reached:** the result is added: "4.6 MB, under your 5 MB (was 59.4 MB)." (re-saved only: "…; the images were not changed.").
- **Already under:** said before the run ("This file is already under 1 MB (512 KB); choose a level to make it smaller anyway.") and Run waits; nothing is made.
- **Cannot be reached:** the smallest readable result (the floor's) is added and selected, with the message's Save and Add buttons: "The smallest readable result is 6.8 MB. It does not fit 5 MB: keep it or remove it, or use Split to divide the file." When text and drawings are the bulk: "…, as most of this file is text: …". When nothing worthwhile can be made: "Cannot fit 1 MB. Most of this file is text, which cannot be made smaller, so nothing was added; Split can divide it." Keeping or removing such a result is the result row and its message, not a question inside the dialog.
- Several files: each is fitted on its own; one message lists what fitted, what did not (kept for the user to decide), and what was already under.
- Signed, protected and form files are handled as for the levels (the signed-file warning; "Signature no longer valid"; the protection notice of 5.1; form fields kept).
- Record: "Compressed to fit 5 MB (93% smaller: 59.4 MB → 4.4 MB)" or "Compressed to the smallest readable size; does not fit 5 MB (…)"; options `targetBytes`, `reachedBytes`, `fitsTarget`, `attempts`, and `dpi` and `quality` when images changed.

Default names say how the copy was made, for the levels too: `<name>_compressed_light.pdf`, `_balanced`, `_strong`, and `<name>_compressed_5MB.pdf` for Fit to a size, following the choice until a name is typed.

### 5.6 Page numbers (phase 1)

Adds page numbers to one file. Default name `<name>_numbered.pdf`. Options:

- **Position**: bottom centre (default), bottom left, bottom right, top centre, top left, top right, with a margin setting.
- **Format**: `1`, `Page 1`, `1 of N`, `Page 1 of N`, or custom text with a prefix and suffix (for example a working-paper reference: `WP-A1 / 1`).
- **Start number** (default 1) and **which pages**: all, or from page X to page Y, so a cover page can be left unnumbered.
- **Font size and colour** (default 10 pt black).
- A live preview inside the Page numbers dialog before applying: a small preview of the first numbered page and a close-up of the number's position.

Numbers are placed relative to each page's own size and rotation, so mixed portrait, landscape and rotated scans all come out right. Existing page content is not changed. Stop takes effect between steps. From phase 2 this tool also places header and footer text and has more number styles (section 5.17).

Phase 1 defect fixed in phase 2: on a page whose own drawing leaves a graphics state open (an unclosed `q`) or a transform in place, phase 1 placed the number in that state, measured 86 pt from where it belonged (12–333 pt in a reviewer's cases). From phase 2 every mark, page numbers included, is drawn after the page's own drawing is closed off, and lands within 1 pt. A page whose drawing has an extra closing `Q`, or cannot be read, may still be misplaced; it is flagged (5.17). The owner chose on 14 November 2026 to correct this in phase 2 only; until phase 2 is merged, `main` has the phase 1 behaviour.

### 5.7 Images to PDF (phase 1)

Turns one or more selected images into one PDF, one image per page, in the order shown in the dialog (section 4). Accepts JPG, PNG, WebP, BMP, GIF (first frame) and, from phase 2, one-page TIFF (below). Options: page size (A4 turned to suit each image, which is the default; same size as each image; A4 portrait; A4 landscape) and margin (default 28 pt, 0 to 279 pt; none for "same size"). A phone photo's stored rotation is honoured. A margin that leaves less than 36 pt of usable area is refused, and "same size" pages are limited to 14,400 pt so that PDF readers accept them. Default name `<first image name>.pdf`. A result of 5 MB or more adds one sentence: "Photos are kept as they are; Compress can make this PDF smaller." Stop takes effect between steps.

**TIFF (phase 2; the lead's recommendation, accepted by the owner on 14 November 2026).** A TIFF is added like any other file (picker, drop, Evidence Vault), with nothing to set. It is converted when it is added, by code written for the module (`tiff.ts`, `tiffCodecs.ts`; no new dependency):

- **One page, upright, square pixels** (the usual scanner or portal TIFF) becomes an image row, as a GIF, WebP or BMP does (PNG; or, when the page is one whole JPEG, that JPEG). It has a thumbnail, opens in the viewer, and works in Images to PDF and Merge.
- **Several pages** (or one page that is turned, or a fax with uneven pixels such as 204 × 98 dpi) becomes **one PDF row** with a page for each picture, each page sized from the scan's resolution. A notice says `"statement.tif" was converted to PDF` / "Its pages are in the list as one PDF. The TIFF itself is not changed." While it converts, the progress line reads "Converting statement.tif (page 2 of 3)…". Images to PDF does not take such a row (it is a PDF); every page tool does.
- The row keeps the TIFF's own name, so results are named `statement_merged.pdf` and the record's sources say `statement.tif [computer]`; its description is "Converted from a 3-page TIFF" or "Converted from TIFF". Saving the converted row itself gives `statement.pdf`, and its record reads "Copy of a file from the computer, converted from TIFF to PDF → statement.tif (…)".
- Read exactly: classic TIFF in both byte orders, every page of the file (reduced copies and masks skipped); bilevel, grey (1, 2, 4 and 8 bits), 8-bit RGB and palette images, with one alpha channel flattened onto white; strips and tiles; no compression, PackBits, LZW and Deflate (with the horizontal predictor), CCITT Group 4, Group 3 (1-D and 2-D) and Modified Huffman; one whole JPEG per page; all eight orientations; resolution in inches or centimetres (a missing resolution gives square pixels sized so the long side fits A4, never below 72 dpi). Fax pages are decoded and stored as 1-bit pictures, so a damaged stream is refused, never shown half-drawn.
- Refused, in one plain sentence: BigTIFF, 16-bit, 32-bit and floating-point samples, CMYK, Lab, old-style JPEG, JBIG and other compressions not listed above. "This TIFF is saved in a form PDF Tools cannot read; save it as PDF, JPG or PNG and add it again." ("Page 3 of this TIFF …" in a several-page file); "This TIFF file is damaged or incomplete; open it in the program that made it, save it again and add it again."; too many pages or too large: "… split it into smaller files and add them again."
- The original TIFF is never changed. Nothing of the file's content goes to the record beyond its name. Limits are in 5.14.
- Measured: a 50-page A4 Group 4 file at 300 dpi (2.61 MB) became a 1.43 MB PDF in 4.9 s run alone, never holding the window for more than 55 ms.

**HEIC** (iPhone photos) stays refused, with one sentence that says how to get a picture PDF Tools can use: "iPhone photos (HEIC) cannot be used here; send the photo from the phone as a JPG, or set Camera > Formats > Most Compatible, and add it again." **(owner decision, 15 November 2026.)** A trial found that nothing built into the application or into Windows on this machine decodes HEIC for the application, even with Windows' own HEIF and HEVC extensions installed; the only route is a decoder library under LGPL-3.0, and HEVC decoding is covered by patent pools, so shipping it needs the owner's licence and legal decision (section 3, candidates).

### 5.8 PDF to images (phase 1)

Turns pages of one file into images, one per page. Options: all or chosen pages; PNG or JPG; resolution 100, 150 (default) or 300 dpi. Results are named `<name>_page_001.png` and so on, and are grouped under one result row that expands to show them. #### Rules added by fix waves 5 and 6

**A value split by a page turn (lead ruling Q).** A value whose first part ends one page and whose second part starts the next is a place on both pages. The turn is read in several ways, and a place found in any reading counts: as written; with the lines both pages repeat left out (headers, footers, page numbers, and a table heading row that the later page repeats, also at another height); with 0 to 4 lines left out at the end of the earlier page and 0 to 4 at the start of the later one, whatever they say; and cell by cell in columns, so that a narration continued overleaf is joined without the amounts beside it. A typed word whose only mention is broken by the page end gets a place on both pages. A few extra places at a page turn are accepted; a missed half is not. Each page that holds a piece is treated like any page with a place.

**A typed value where a letter cannot be read (lead ruling R).** Some fonts give no letter for a joined character of an Indian script, so the page text holds an unreadable glyph there. A typed value in that script is matched with each such glyph standing for up to three letters of one word, and a match is a place like any other. If a typed value is still placed nowhere and the pages being redacted hold unreadable text of the same script, every unreadable run of that script on those pages is covered whole, not the single glyph alone; fix wave 4's single-glyph rule applies only when every typed value of that script was placed. A typed word found nowhere is never dropped silently: under the word chips the review shows "Not found: 2 typed words." (for one, "Not found: 1 typed word."), each such chip is marked "· not found", and the confirmation repeats the line.

**Account and card numbers (lead ruling T).** Account numbers are compared without leading zeros (nine digits are always kept), so a number written with zeros in a header also takes the same number in the narrations. The key stays short and the covered area long: the value in the list is the number as far as its own digits surely go, and at every place the box runs on over the digit groups written right after it, one space or one hyphen apart or at the start of the next line, until something that is not a digit group of the number. An amount, a date, a time, a rate, a figure in another cell, and digits beyond what the kind can have (18 for an account, 19 for a card) are not covered. Right after an account label the groupings 4-4-6, 3-4-4 and 2-4-4-4 are read as one number.

**Labels (lead ruling U).** Also read, as *possible* unless stated: the name after "Name and address of the Employee" and similar Form 16 labels, with the lines down to the PIN code as an address; the names under a "Name" column heading; a name on the line under a "Name" label, and a valid date at the start of the line under a birth-date label (sure); the dates under a wrapped "Date of / Birth" heading; a 15-digit number in the cell under an acknowledgement heading (sure); an account number beside an IFSC under a heading that names the account; the names, account numbers and birth dates in the next cells of a row whose first value has a label; the addressee after a designation line when the name starts with a title (Shri, Smt, Mr, Mrs, Ms, Dr), found later without the title too; a number of 9 to 18 digits alone in its cell after a label in an Indian script (a mobile number when it has that shape, otherwise an account number). The four reasons shown with these matches are: "under a column heading that names it", "the line under a "Name" label", "in the same row as a value with a label" and "a number after a label in an Indian language".

**Waiting and a busy machine.** While typed words are being searched the list shows "Searching for your words…", and Redact and the confirmation's Redact are disabled with "Wait until your words have been searched." The find and the run give the window a turn by the clock on long files. A read or a drawing that the renderer could not finish because the machine was busy is tried again twice; the sentences are below.

**Sentences added or changed in fix waves 4 to 6**, as the code has them (page numbers are examples):

- Review and confirmation: "Not found: 1 typed word." / "Not found: 2 typed words."
- Review: "Wait until your words have been searched."
- Confirmation, when other pages may not be copied unchanged: "1 area on 1 page will be removed. Page 1 will become a picture of the page; pages 2-20 will also become pictures, to be safe." (for one page: "; page 2 will also become a picture, to be safe"). Until those pages have been read: "; some other pages may also be made pictures, to be safe.", and the size line reads "The new file is at least about …".
- Confirmation: "On page 1, some text Redact cannot read will be covered too."
- Confirmation: "Hindi and ₹ on the redacted pages stay visible in the picture but cannot be searched."; where the pages have no Hindi: "Some scripts and symbols on the redacted pages stay visible in the picture but cannot be searched."
- Result: "Page 4 was also made a picture, to be safe."
- Result: "On page 1, some letters that could not be read were covered, to be safe." The sentence "On page 1, text or a drawing that could not be read was covered whole, to be safe." is shown only when a whole run was covered.
- Result: "Some text on the redacted pages cannot be made searchable (for example Hindi and ₹)." where the redacted pages have Hindi; otherwise "Some scripts and symbols on the redacted pages cannot be made searchable." " It is still visible." or " They are still visible." is added only when none of that text was covered.
- Result: "Page 2 is a scan with hidden text: where that text misread a value, the scan may still show it, so look at the page."
- Find, busy machine: "The computer was too busy to search this file. Close other programs, then search again."
- Run, busy machine: "The computer was too busy to finish. Nothing was added. Close other programs, then try again."

Only the boxes you draw remove anything there.", and while such a page is shown a line over it says "Automatic finding cannot read this page: only the boxes you draw remove anything on it."
2. **Reviewing.** Proposals are shown as outlined boxes on the page and as rows in the list (below). Ticking and unticking, drawing and deleting boxes all happen here, with undo and redo.
3. **Choosing the output** (below) and pressing **Redact**. A confirmation step lists what will happen ("14 areas on 3 pages will be removed. Pages 2, 5 and 7 will become pictures of the page; the other 37 pages are copied unchanged.") with any warnings, the result's name, and the buttons **Redact** and **Back**. Pages that may not be copied unchanged are named in the same sentence ("…; pages 2-20 will also become pictures, to be safe."), and typed words placed nowhere are counted ("Not found: 1 typed word."). Redact is disabled while typed words are still being searched.

#### What is searched

The text of every page, including text that is hidden (white on white, invisible text, text in a layer that is turned off) and text outside the visible page area (pdf.js leaves that out, so the search opens a copy of the file whose pages have no crop box). Also the text of comments and their authors, form field values, and link addresses (as pdf.js reports them: `contentsObj`, `titleObj`, `textContent`, `fieldValue`, `url`). A match in a comment, field or link becomes a box over that comment's, field's or link's area; a comment whose rectangle covers more than 95% of the page is not used as a box: the value is placed where the comment draws it, or the run asks or stops before any work. Text drawn as pictures (scans) or as outlines cannot be searched. The file's name is searched too (below, "Result and record").

The patterns themselves are in `src/lib/pdf-tools/redactPatterns.ts`.

Aadhaar's check digit uses the Verhoeff algorithm; GSTIN's uses `calculateGstinCheckDigit`. The application's own `isValidGstin` is not used for the decision, because it refuses state code 38 (Ladakh) and codes 96 and 99 and requires `Z` as the 14th character; a GSTIN-shaped value it would refuse is still proposed, as *possible*. Whether the GST entry points themselves should accept those codes is a separate question for the owner (section 12); `src/lib/gstinValidation.ts` is not changed.

Codes and numbers are also found when written with a space between every character (letter-spaced or boxed), and with up to three separators between characters.

**Your own words.** Up to 20 terms typed by the user, each 3 to 100 characters, each with an optional reason label (default "Typed"). The rule under the field: "Found as whole words, whatever is between them: spaces, punctuation, a line break or nothing, and across a word broken by a hyphen at a line end. Also looked for in the file name." So a typed name is found with spaces, a line break, any punctuation (dots, underscores, commas, dashes, slashes, colons, "&", brackets) or nothing at all between its words, but never inside a longer word. Every match is ticked. The same rule is used by the find, by the run's net and by the check, on every page and on the file name **(lead ruling, 15 November 2026: one matching rule everywhere)**.

**Profiles**, chosen at the top of the list (`redactView.ts`):

- *Balanced* (default): "Identity numbers, contact details, bank and tax numbers ticked; addresses, IP addresses, payroll, investment, company and document numbers listed for you to tick."
- *Strict*: "Everything found is ticked, except company and professional numbers and codes that are usually part or branch numbers." Every group but Company and professional numbers is ticked, possibles too, except the held kinds (TAN-like and IFSC-like codes, account numbers that only sit next to an IFSC, unlabelled twelve-digit numbers that pass the Aadhaar check, PAN-shaped codes written with a space between every character and no label, and the held added kinds above) **(lead ruling)**.
- *Identity numbers only*: "Identity numbers ticked: PAN, Aadhaar and its virtual ID, GSTIN, TAN, passport, voter ID, driving licence, date of birth and tax document numbers."
- *DPDP personal data* (**owner decision, 14 November 2026**): "Everything about a person ticked, possible matches too: identity, contact, bank, payroll, investment and vehicle numbers, names, addresses and IP addresses. Company numbers and tax and GST document numbers are listed for you to tick."

Company and professional numbers are ticked by no profile (**owner decision, 14 November 2026: business identifiers off by default**); the options show that group apart, saying so. The profile last used is remembered on this computer (the profile name only, under the localStorage key `pdfTools.redact.profile`; lead ruling); no value, term or file is ever stored.

#### Every occurrence

A value found once is searched on every page, and each occurrence is proposed, so a PAN seen on page 1 is also boxed on page 40. The list groups the occurrences under their value: "BNZPM2501F · PAN · 3 places (pages 1, 4, 7)". A group's tick turned on ticks the places the group ticks by default and leaves every other tick as it is; turned off it unticks every place of the group; each place can also be unticked on its own.

If a value is ticked in some places and unticked in others, the confirmation step says: "BNZPM2501F stays visible in 1 place you unticked (page 7). The redacted file will still contain it there." The user can go back or go on. Such a value is not part of the guarantee below, and the record counts it (never names it). This is how the "must never happen" rule of section 3 is read: the redacted text is text the user chose to redact everywhere.

A box the user draws removes its area only. When the text under it is a single value-like word (no space; at least 4 characters with a digit, or at least 6 characters), the box's row offers "Redact this text everywhere"; only if the user chooses it are that word's other occurrences proposed, ticked, in a group "Same text as your boxes", and they go when the box goes **(lead ruling)**.

#### Boxes

- A match gives one box per line it covers. Boxes on the same line that overlap or touch are joined, so a value written as three groups is one box.
- A box is the match's characters, placed by the width of each character in a font of the same family (Arial for sans-serif, Times New Roman for serif, Courier New for monospaced), scaled to the width pdf.js gives the text, from 0.25 em below the baseline to 0.9 em above it or the font's own descent and ascent if larger, **plus 1.5 pt on every side**. The trial needed at most 0.41 pt to cover all the ink.
- Text that is not painted (wholly outside the visible page area, or text the tool can prove is invisible) is removed without a box. Any other matched text gets a box, even when its area looks blank in the rendering: faint text (grey 0.97 on white) would otherwise stay in the picture **(lead ruling)**.
- Each text box is grown along its text on the page's drawing until neither end cuts a glyph; underlines, table rules and the next line's ink are ignored. A box that cannot be closed that way is widened to its whole line of text, and the result says so ("1 box was widened to the whole line, to be sure nothing of the text shows."). Where a font's widths cannot be judged, the box also covers a per-character estimate. Boxes placed from what a drawing paints keep 3 pt. Every pixel of every box is checked black before the page is encoded.
- An automatic box covering more than 95% of the page is dropped, with the note "1 automatic box covered almost the whole page and was left out. Draw a box if you mean it." A drawn box may cover the whole page.
- Boxes the user draws: one button, "Add a box", with two small choices beside it, a mouse (chosen to start with) and a keyboard (owner decision of 16 November 2026, in place of the two buttons "Draw boxes" and "Add a box"). With the mouse the button switches drawing on and off: drag on the page. The button is on while drawing is on or a keyboard box waits, and choosing the other way while it is on carries on in that way at once. A waiting box the user has moved or resized is added, as Enter would add it, when the user goes to the mouse or switches the button off; one never touched is dropped; Escape always drops it. With the keyboard it puts a box on the page to place before it is added (arrows move 1 pt, Shift 10 pt, Alt resizes, Enter adds, Escape drops). A box smaller than 2 × 2 pt is ignored. A box already added cannot yet be moved with the arrows.

#### The list and the review

Rows show the kind as a coloured label (PAN, Aadhaar, …, Typed, Drawn, Same text), the value as written, the page, and the reason for *possible* matches. Controls:

- tick or untick a place, a value (all its places), a group, or everything;
- a filter box (matches kind, value or page number);
- "Show unticked" (on by default);
- choosing a row shows its page and highlights its box; clicking a box on the page selects its row;
- delete a drawn box (Delete key or its row's button); "Clear drawn boxes on this page"; "Clear all drawn boxes";
- undo and redo of every change in the dialog (Ctrl+Z, and Ctrl+Y or Ctrl+Shift+Z), up to 100 steps **(design call)**.

On the page: a proposal is an outlined box (blue for sure, dashed amber for possible, grey when unticked); a ticked box is filled half-transparent black; the selected box has a thick outline. The opacity on screen is fixed **(design call)**.

#### Remove or Replace

- **Remove** (default): a black box.
- **Replace**: a black box with the replacement in white, bold, along the text's direction (along the page as displayed, for drawn boxes) **(design call: black with white text, so that a replacement can never be mistaken for the document's own text)**. The replacement is one of:
  - **Token** (default): `[REDACTED]`, editable, 1–30 characters of letters, digits, spaces and `[]()-/.`. A custom token is never recorded (it could hold a value).
  - **Label by kind**: `[PAN redacted]`, `[Aadhaar redacted]`, `[GSTIN redacted]` and so on for every kind, and `[REDACTED]` for typed terms and drawn boxes.
  - **Masked value**: the letters and digits of the value written as X except the last four: `XXXXXX501F`, `XXXX XXXX 0124` (Aadhaar keeps its groups); a card or VID as `XXXX XXXX XXXX 1234`; a date of birth as `XX/XX/XXXX`; a UPI ID with its handle only; an email with the first letter of the name, then `*****@` and the domain. Typed terms and drawn boxes use `[REDACTED]`. The dialog says: "Masked values show the last four characters. Use Token or Label if even those must not appear."
- The replacement is drawn at the largest bold size up to 70% of the box height that fits its width, but not below 4 pt. If it does not fit, the box stays plain black; the result says "3 replacements did not fit and were left as plain black boxes."
- The replacement is drawn into the page picture only. It is not added to the text layer **(design call)**.

#### Output

- **Form**: *Searchable* (default) or *Picture only*.
  - *Searchable*: each page with at least one ticked box becomes a picture of the page with the boxes burned in, plus an invisible text layer made of the words on that page that touch no box and are not part of a redacted match. The rest of the page stays searchable and selectable.
  - *Picture only*: the same pictures, no text layer. Both forms get the same boxes and the same checks.
- **Resolution**: 150, 200 (default) or 300 dpi, under "More options" with a closed line such as "200 dpi, about 1.2 MB". The dialog shows the expected size, worked out from the characters on each page to rebuild: at 200 dpi about 20 KB a text page plus 80 bytes a character, and 800 KB for a page without text; 0.6 times that at 150 dpi and 2.3 times at 300 dpi. Under 200 dpi the options say "About 100-300 KB a page of text, more for dense or coloured pages." On bank statements test 5 measured the promised size about 4 times too small (11a).
- **A result whose copied pages had to keep their resources whole is not added**: the original picture of a redacted page could ride along in a shared resource. The message says "Some pages could not be read with certainty, so parts of the redacted pages may still be inside the file. Nothing was added. Print the file to a new PDF and redact that copy."
- Each rebuilt page's picture is stored both ways and the smaller kept: lossless (Flate; grey when the page has no colour) or JPEG at quality 0.85. Text pages come out lossless, scans as JPEG.
- The rebuilt page has the old page's visible area as its page size and the old rotation. Its comments, links and form fields are drawn into the picture as they appear on screen and are not kept as such; a field that lived only on that page leaves the form.
- On a rebuilt page the text is a picture at the chosen resolution, so it is softer than the original when zoomed past that resolution, and the file is larger; in the searchable form the remaining text can still be searched, selected and copied. Plain pages without a box are copied unchanged (below). Removing text from the page content itself (as the owner's earlier tool did, with a library this application cannot bundle; section 13) was not proven possible here and is not proposed **(design call)**.
- The text layer uses the standard Helvetica font, which only has Latin characters (Windows Latin-1). Characters it cannot hold, such as Hindi and the rupee sign, are left out of the text layer. They remain visible in the picture, with one exception: a character for which the font gives no letter (some joined Hindi letters) is covered, by itself when every typed value of its script was placed, and with its whole run when one was not ("Rules added by fix waves 5 and 6", above); the confirmation says so before the run ("On page 1, some text Redact cannot read will be covered too."). The result says "Some text on the redacted pages cannot be made searchable (for example Hindi and ₹)." where the redacted pages have Hindi, and "Some scripts and symbols on the redacted pages cannot be made searchable." where they have none; " It is still visible." or " They are still visible." is added only when none of that text was covered. The record is flagged `textLayerIncomplete`.

Pages without a ticked box are copied by the page copy of Split and Delete pages (5.3), unchanged in appearance, with their comments, links and form fields, when they are plain (fix wave 4's allow-list). A page that is not plain is rebuilt as a picture although it holds no chosen value: the confirmation names it before the run and the result says "Page 4 was also made a picture, to be safe." The following is removed from them, because none of it can be checked: comments that hold attached files, sound, video, 3D or rich media; `/Redact` marks left by other programs (the marked area is proposed as a box instead, ticked, labelled "Marked for redaction in the file", where pdf.js reports the mark); page and comment actions other than going to a page or opening a web address (scripts, launching files, submitting forms); private application data (`/PieceInfo`); XMP metadata on pages, images and drawings; page thumbnails.

The result carries nothing else of the source document: no document properties except Producer and Creator "ICAI VERA"; no XMP metadata; no attached files; no document scripts or open action; no named destinations; no page labels; no tagged structure (accessibility tags; their alternative texts are checked before the tree is dropped); no article threads; no earlier saved revisions. Bookmarks are carried by the rules of 5.10. A bookmark whose title contains a redacted value, in any of the forms the check looks for, is removed, not masked, with the bookmarks under it moving up one level; the number removed is recorded (`bookmarksRemoved`), and the check searches bookmark titles like every other string **(lead ruling)**. A bookmark to a page that is rebuilt as a picture stays and still opens that page.

#### The check

Before anything is drawn, the run reads every page's drawings one by one (each annotation's appearance, every instance of it, each form and tiling pattern the page draws, each Type 3 glyph procedure, text in a font whose character map cannot be trusted, and alternative text, inline or on structure elements), each as joined text in drawing order and across lines, or as "cannot read" with a reason (an abbreviated or unknown filter, an object that cannot be parsed or is defined twice, a font with no usable map, a Type 3 glyph that draws a picture). A copied page whose drawing holds a chosen value is boxed where that drawing paints before the first build and then proved like a rebuilt page.

**The proof on every rebuilt page (from fix wave 2).** The run makes two copies of the source: one from which every rebuilt page is drawn, and one in which everything that draws a chosen value is made invisible: every show of text whose string holds a value in any reading (and runs of up to 16 shows whose joined reading holds one, such as a name over two lines), marked content whose alternative text holds a value, and every painting stream or object that cannot be read (emptied: "cannot read" means covered whole). In page content only the value's own characters are hidden, so the words beside it stay. Both copies are drawn at the run's resolution; every pixel where they differ must lie inside a box, and where it does not, a padded box is added there. If that would cover more than 60% of the page, the run stops and adds nothing ("The redacted file could not be verified: page 3 draws redacted text over most of the page, where no box can be placed. Nothing was added. Untick that value, or print the file to a new PDF and redact that copy."). A covered place never vouches for another drawing of the value. Alternative text whose marked content cannot be found on its page is asked about (below). When something was covered beyond the places found, the result says so in one sentence: "On page 3, a chosen value also showed outside the places found; it was covered there too." or "On page 1, text or a drawing that could not be read was covered whole, to be safe." (only when a whole run was covered; when single unreadable letters were covered: "On page 1, some letters that could not be read were covered, to be safe.")

After the file is written, and before it is added to the list, the tool checks it:

1. **Structure.** Every rebuilt page holds only its picture, its text layer and the Helvetica font; no comments, actions, metadata or other resources.
2. **Text, as a reader sees it.** pdf.js opens the result and reads: every page's text (from a copy without crop boxes), comments, field values, link addresses, bookmark titles, document properties and XMP, attachments, scripts, page labels and destination names.
3. **Every string in the file.** Every string and name in every object, decoded (escapes, UTF-16, character references in rich text, `+` and percent escapes in web addresses); every stream that is not an image, decompressed; inside content streams, every string decoded and the pieces of each `TJ` array joined, and the strings of a stream also read joined; all of it also with NUL characters removed.

Each redacted value is looked for in its forms: the value as written; without spaces and hyphens, in capitals; for Aadhaar the 12 digits plain and grouped 4-4-4 with a space and with a hyphen; for mobile the 10 digits plain and grouped 5-5; for cards and VIDs also grouped 4-4-4-4; for email and UPI IDs, lower case; for typed terms and text the user chose to redact everywhere from a drawn box, by the one matching rule above. The check uses the find's own rule and the same loose rule for every page and the file name; each kind keeps the separators that belong to it (IP addresses, email addresses and document numbers keep theirs; codes are compared without them) **(lead ruling)**. The picture of a rebuilt page is not searched as text; the proof above covers what it shows.

What happens when the check finds something (lead rulings):

- A value found on a page that was copied unchanged is covered there: by the rectangle the file gives (a comment, a field, a link) or, for page text, by the find's own placing of it; the page is rebuilt with those boxes and checked again, at most three times. The result says "Page 4 also held redacted text the review did not list. It was covered there too, and the page was made a picture."
- A value that is not drawn on the page (hidden alternative text, private data) and cannot be boxed is offered for flattening: the dialog names the pages, shows them, and asks "Flatten this page?": "Page 2 holds redacted text that is stored in the page rather than drawn as text Redact can read (for example alternative text or a layer's name), so no box can be placed for it. Flattening makes the page a picture of what it shows now, which removes that stored text." When the page may show it in a form Redact cannot read, the question adds "This page may show it in a form Redact cannot read. Look at the page: if you can see it, choose Do not flatten, draw a box over it and run Redact again." Only on the user's word is each page rebuilt as drawn, without boxes, and checked again; the result and record say so ("Page 2 was flattened, as you confirmed."). Flattening never drops a page's boxes.
- A value that is drawn but cannot be placed, or is found anywhere else, or is still found after the rounds: the result is discarded and nothing is added, with advice that is true: "The redacted file could not be verified: redacted text was still found in it (page 4, bookmarks). Nothing was added. Untick that value, or print the file to a new PDF and redact that copy." ("Draw a box over that text" is offered only for text the find reads on a copied page.) Never a silent pass; no message names a value.
- A run that shows no sign of work for 120 s of active time ends with "Redact stopped because a page took too long to draw or read. Nothing was added. Try again; if it happens again, restart the application." (time asleep, a hidden window's slowed timers and waiting for the user's answer do not count). A drawing the renderer refuses ends with "A page could not be drawn for redaction. Nothing was added. Try again; if it fails again, restart the application." A drawing or a read that the renderer could not finish because the machine was busy is tried again twice; if it still fails, the run ends with "The computer was too busy to finish. Nothing was added. Close other programs, then try again." and the find with "The computer was too busy to search this file. Close other programs, then search again." Neither blames the file.

**What is guaranteed**: no value the user chose to redact everywhere, no text the page showed under a ticked box, and none of the document-level information listed above remains in the result in any form the checks can read, and no rebuilt page shows, outside a box, anything that draws a chosen value. **What is not guaranteed**: text the file shows only as pictures or outlines (scans, drawn text, a Type 3 glyph that draws the value as outlines only) unless the user draws a box over it; values the user chose to keep visible somewhere; information inside images on pages copied unchanged (for example a photo's own camera data); a font whose character map gives other plausible letters with no glyph names to compare; characters written out of reading order; a value split by other text in reading order (two columns); a typed name glued to the word before it; look-alike letters from another alphabet and Devanagari digits in another copy of a value; encoded copies of a value (base64, reversed text) inside links and comments; and other PDF readers' behaviour, which was not checked. The guarantee did not hold in the sixteen cases B1 to B8 and R1 to R8, nor in the blocking findings of tests 3, 4 and 5, above; each was fixed. No separate independent round has run since the last fixes (Status, above), so this list states what is known at revision 8; 11a adds the limits found in fix waves 5 and 6.

### 5.10 Bookmarks (phase 2)

Two trials showed that bookmarks can be read, written and carried with `pdf-lib`'s own objects, with no new package, and that pdf.js reads the written result back with the same tree, titles and pages. On a 500-page file with 2,000 bookmarks, reading took 24–55 ms and writing 20–66 ms; the cost of the Bookmarks tool is loading and saving the file. Rules marked **(lead ruling)** were decided by the lead on 14 November 2026.

#### Reading a file's bookmarks

- Bookmarks are followed through `/First` and `/Next` only; `/Last`, `/Prev`, `/Parent` and `/Count` are not trusted (the sign of `/Count` still says whether an item is open). A loop, an item that is its own first child, a missing or wrong `/Count` and a missing `/Last` are tolerated: the reader stops a loop and counts it, and never throws or hangs.
- Destinations are followed whether written as a page and view (`/XYZ`, `/Fit`, `/FitH` and the others, kept as written), as a name (in the `/Names` tree, including `/Kids` and `/Limits`, or the older `/Dests` dictionary, including a value that holds `/D`), as a GoTo action, direct or as a separate object. A destination whose page is not in this file's page tree, a missing name, a page number that points into another file, and actions that open another file, launch something or run a script give "no page". (pdf.js reports page 1 for a destination whose page object is not in the page tree; the list beside the page panel uses PDF Tools' own reader for that reason.)
- Titles are decoded from PDFDocEncoding, UTF-16 (either byte order, with its byte-order mark) and UTF-8 with its mark. A title longer than 1,000 characters is cut there when read. Titles may be in Hindi and hold ₹ (checked from the saved bytes).
- Limits: 10,000 bookmarks and 32 levels. A file over either limit can still be used by every tool, under the rules below.
- Bold, italic and colour of a bookmark are read and written back.
- The file is read in a background worker (a module worker with its own copy of pdf-lib), 1,500 objects at a time: pdf-lib's default of 100 made a 320-page ledger with no bookmarks wait 163 times for a timer, 20 to 30 s on a busy machine; it now takes about 3 s. The worker says every second that it is still reading; the reading is given up only when it says nothing for 30 s ("Reading the file stopped answering. Nothing was changed."), and it ends when nobody waits for it. After 5 s the dialog says how long it has taken. A file found without bookmarks when it was added is never said to have bookmarks that "could not be read" (its dialog's title is "Bookmarks cannot be added yet" while it is read); after a stopped reading, the action bar says "The file has to be read again first: press Try again."

#### The Bookmarks tool

Works on exactly one PDF. The dialog shows a page strip of its own (left; one Tab stop; arrows, PgUp, PgDn, Home and End choose the current page; Enter or the corner icon opens the viewer) and the bookmark tree (right). The strip's header holds a page number box ("Page [n] of N", named "Go to page, 1 to 320"): type 212 and press Enter to make page 212 the current page and bring it into view, ready for "Add for page 212"; a page not in the file is said as in the viewer. Choosing a bookmark shows its page and brings it into the strip, also when it already was the current page.

Actions on the tree, each by mouse and by keyboard, read out in a polite live region, as is why nothing happened:

- **Add** a bookmark for the current page (also Insert), after the selected bookmark at the same level (or at the end). Its title starts as "Page n", selected for typing. It goes to the top of the page, at the reader's current zoom (`/XYZ left top null`).
- **Rename**: Enter or F2 on a bookmark. Titles **(lead ruling)**: at most 256 characters as typed (counted in characters, never cutting a character in two); control characters and line or paragraph separators become a space; bidirectional override characters, the zero-width space and the byte-order mark are removed; the zero-width joiner and non-joiner are kept, because Hindi needs them; spaces are collapsed and trimmed; a title left empty is refused ("A bookmark needs a title."). Any language may be used.
- **Move up** and **Move down** within its level (buttons and Alt+Up / Alt+Down).
- **Indent**: make it a child of the bookmark above it (Alt+Right); **Outdent** (Alt+Left). The user can nest one level, as the owner's design says: a bookmark can be indented only under a top-level bookmark ("Only a top-level bookmark can be indented: bookmarks nest one level."), and a bookmark that has bookmarks under it cannot be indented. Bookmarks the file already has at deeper levels are kept and shown at their depth, never flattened; they can be renamed or removed and move with their parent **(lead ruling)**.
- **Remove** (Delete key; Backspace does not); removing a bookmark that has bookmarks under it asks first: "Remove 'Notes' and the 4 bookmarks under it?" with "Keep" and "Remove".
- **Go to page**: choosing a bookmark shows its page.
- Undo and redo (Ctrl+Z; Ctrl+Y or Ctrl+Shift+Z), up to 100 steps.

The action bar and the tree are one Tab stop each. An unavailable action keeps its focus and says why on hover, focus and click. Closing with unsaved changes asks "Discard your changes?" ("Keep editing", "Discard changes"). Titles over 1,000 characters, cut when read, are named in a "Long titles" notice.

A file without bookmarks opens with an empty tree and the hint "Add a bookmark for the page shown." Bookmarks that go to a web address are kept as they are. Bookmarks that open another file, launch something or run a script are shown greyed with "Not carried" and are dropped when the file is saved; the dialog says "2 bookmarks that open other files or run scripts will not be kept." **(lead ruling)**.

A file with more than 10,000 bookmarks or nesting deeper than 32 levels cannot be edited, because saving would lose the bookmarks that were not read: "This file has more bookmarks, or deeper levels, than PDF Tools can edit (10,000 bookmarks, 32 levels). Nothing was changed." **(lead ruling)**. It opens read-only: the bookmarks are shown, with no actions, no key hints and no result name, and the Save button says why it cannot be used.

Saving writes the new bookmarks into a re-saved copy of the source, with a turn for the window at least every 50 ms of work: the old outline is unlinked, then its own objects are deleted (the items reached from its root whose parent chain leads back to it, their titles, and the actions and destinations only they use, and of those only what nothing else in the file refers to), so a removed or renamed title is gone from the saved bytes. A damaged outline that runs into other objects never makes the save delete them: anything not certainly the outline's own stays in the file, unlinked, and the result says: "Some old bookmarks could not be removed safely; their titles may still be in the file's data, though no reader shows them." The record notes "some old bookmark titles may remain in the file". Titles are always written as UTF-16 (big-endian, as hex strings) **(lead ruling: the trial found that writing them as plain strings corrupted non-Latin titles)**. `/Count` follows the PDF rules: an open bookmark counts the bookmarks visible under it, a closed one is negative, the root counts the visible bookmarks. The file opens with the bookmark panel shown (`/PageMode /UseOutlines`) when it has bookmarks and its page mode was unset or "none"; when no bookmark is left and the mode was "outlines", the mode is removed. Named destinations in the file (`/Dests`, `/Names`) are not touched. Everything else in the file is re-saved as it is, like Page numbers, so it keeps earlier saved revisions (section 11) and a signature becomes invalid: "Saving changes the file, so its digital signature will no longer be valid."

The Run button names the result ("Save 6 bookmarks", "Save with no bookmarks"); while nothing has changed it says "Nothing has changed yet, so there is nothing to save." (a change undone, or a title renamed back, is not a change). The saved file's bookmarks are read back and compared with what was asked (tree, titles, pages, web addresses); a difference adds nothing. Default name `<name>_bookmarked.pdf`. The result message is "Bookmarks saved:" with the result's name, then "It has 6 bookmarks.". Record: "Bookmarks edited: 12 bookmarks", with the counts `bookmarks`, `added`, `renamed`, `moved`, `removed` and `notCarried`, numbers only, never a title; "; some bookmarks not carried" is added only for the file's own bookmarks that could not be kept, never for the user's removals.

What a rewrite does not keep: links from a bookmark to a structure element (`/SE`), actions other than going to a page or a web address, and PDF 2.0 language marks inside titles. The dialog's "Not carried" line covers the actions; the others are rare and not shown.

#### Carried by other tools

Split (each part and each file), Delete pages, Organise pages, Merge (when asked) and Redact rewrite the outline of their result as follows:

- A bookmark to a page in the result keeps its title, view, bold, italic, colour, open or closed state and children, pointing at that page's new position. A page that appears twice (Split with a page typed twice) is reached at its first copy.
- **A bookmark whose own page is left out is dropped, even when bookmarks under it point at kept pages; those are moved up one level, in order, to take its place (lead ruling: a title naming a removed page must not survive, by the same principle that nothing of a left-out page is carried).** A bookmark with no kept page under it is dropped with everything under it.
- When pages are reordered (Organise pages, Split with pages in a chosen order), bookmarks keep their own outline order, each pointing at its page's new position; they are not re-sorted by page **(lead ruling)**.
- A web-address bookmark is kept as it is. Bookmarks that open another file, launch something, run a script, or go to no page are dropped **(lead ruling)**.
- A named destination becomes a direct one.
- In Merge, each file's bookmarks are offset to the file's first page and, when chosen, put under that file's bookmark (5.2).
- A source over the reading limits (more than 10,000 bookmarks or deeper than 32 levels): Split, Delete pages, Organise pages and Merge carry none of its bookmarks and say so through the flag and note below; they never carry part of them silently **(lead ruling)**.
- Redact: see 5.9; a bookmark whose title contains a redacted value is dropped **(lead ruling)**.
- Split into Equal parts, into a separate file for each range and at bookmarks counts a bookmark that belongs to another part as information only (`bookmarksInOtherParts`), not as "not carried"; a bookmark that goes to no page, or to a page that is in none of the files, is counted once, on the first part. When a bookmark is deleted on rewrite, the action and destination objects that only it used are deleted from the bytes too.

`bookmarksDropped` is set, and the note "; some bookmarks not carried" added, only when at least one bookmark of the source is not in the result.

### 5.11 PDF to Excel and PDF to Word (phase 3)

Both work from the text in the file; a scanned file must be made searchable first, and the tool says so.

- **PDF to Excel.** Text is placed into rows and columns by its position on the page, one worksheet per page or all pages on one sheet (user's choice). Numbers are written as numbers where they parse unambiguously, with Indian digit grouping understood. A preview of the detected table is shown before saving. Stated limit: tables without clear column alignment may need tidying.
- **PDF to Word.** Text is written as paragraphs and simple tables in reading order, with headings and page breaks kept. Stated limit: it is an editable text version, not a copy of the page layout.

Results are `.xlsx` and `.docx` files and go to the same three destinations. Design inputs from the owner's earlier tool (table detection from ruling lines, row and column clustering, fallbacks) are recorded in section 13.

### 5.12 Make searchable, OCR (phase 3)

Turns a scanned file into one whose text can be searched, selected and used by Redact and the Convert tools. The pages look the same; recognised text is added invisibly behind them. Recognition runs on the machine with the language data shipped in the installer: English and Hindi **(design call; other languages on request, each adds to the installer size)**. ### 5.15 Organise pages (phase 2)

Added by the owner on 14 November 2026 ("rotate and reorder pages"). One tool, on exactly one PDF, that reorders, rotates and removes pages in one dialog **(design call: one dialog instead of separate Rotate and Reorder tools, because users do these together; the owner chose this grouping on 14 November 2026)**. Merge does not gain page-level ordering: merge first, then organise the merged result **(design call)**. The word on screen is **Rotate** (owner's word; lead ruling); the record key `turned` and the test ids stay.

**The dialog** (`OrganisePagesDialog.tsx`, `organise/`). The grid's pages are drawn before the page panel's behind it, and a page the panel has drawn shows at once. Pages are chosen by click, Shift+click (a range) and Ctrl+click.

Arrows, Home, End, PgUp and PgDn move the focus; Space chooses; Shift with those keys extends a range; Ctrl+A chooses all; Backspace removes as Delete does; Ctrl+Shift+Z also redoes; Enter opens the viewer. The VERA Tools tab keys are held back.
- Move to position counts pages of the result, not removed tiles ("Page 1–300", with the rule shown next to the box): the way to move across a long file. Dragging tiles with the mouse also reorders (the browser's own drag and drop, no new library), within the 200 tiles shown; it is an addition to the buttons and keys, never the only way.
- The summary line reads, for example, "2 moved, 2 rotated, 1 removed · 4 pages in the result"; "moved" counts the fewest pages that had to move. Every edit is announced ("Moved. Page 3 (was page 7), position 3 of 40", "Rotated right…"); screen readers hear "rotated right", "rotated left" or "rotated 180°".
- The Run button names the result ("Save 4 pages in the new order", "Save 5 pages with 1 rotated", "Save 9 pages without the 3 removed pages"). With nothing to do it stays focusable and says "Nothing to do yet. Move, rotate or remove a page first."; with every page removed, "You cannot remove every page. Keep at least one." The result name is under "More options".
- The notice says what is kept. Rotating only: "The pages are rotated in the file itself, so its bookmarks, links, form fields, page labels and attachments are all kept." A move or removal: what is not carried over, and, when the file has attachments, "Attachments in the document's list are kept when pages are removed."

**The result** (`pageOrder.ts`; lead rulings):

- Rotating pages only is done in the file itself: a rotation adds to the page's own `/Rotate` (kept a multiple of 90) and the page is not redrawn; everything in the file is kept, except content that earlier saved revisions left and the file no longer uses.

### 5.16 Watermark, stamp and logo (phase 2)

Added by the owner on 14 November 2026. The toolbar's "Watermark" button, a "soon" button in phase 1, is this tool. It works on exactly one PDF and has three parts, each with its own switch; at least one must be on **(design call: watermark, stamp and logo are all marks placed anywhere on the page with a size, angle and transparency; header and footer text belongs with the page numbers, 5.17, because both use the page margins)**. Each part's text, ready-made texts and switch are in view; font, size, angle, colour, opacity, layer and position are under that part's "More options", whose closed line shows the values ("Helvetica bold, auto size, diagonal, grey, 25% opacity, in front, centre"). The fold opens by itself when a field inside it is wrong. The Run button names what it does ("Add watermark to 5 pages", "Add stamp and logo to page 1").

**Watermark** (on by default):

- Text: DRAFT (default), CONFIDENTIAL, COPY, FOR AUDIT USE ONLY, NOT FOR CIRCULATION, the engagement's client name, or custom text of 1–60 characters. The "Client name" choice puts the token `{client}` into the text, never the name itself; the name appears only in the "Prints as …" line, the preview and the PDF, filled in when the file is written, so the record keeps `{client}`. The tokens `{date}` and `{client}` (5.17) may be used in the watermark text as well as the stamp; names are not case-sensitive; any other name in braces is refused by name. `{date}` is written in the format chosen in the dialog, DD-MM-YYYY by default.
- Letters, digits and common punctuation only: the built-in fonts cover Latin text. Anything else is refused with the words as typed and what works today: "“मौसम” and “₹” cannot be printed in the watermark text; use English letters, digits and common signs (write Rs. for ₹)." (at most three words, then "and N more words"; only characters that print as nothing are named by code, "Invisible characters (U+200B)").
- Font Helvetica (default), Times or Courier; bold (on by default) and italic.
- Size: Auto (recommended; the largest size whose text fits 80% of the line it runs along across the page as displayed and whose turned box stays within 90% of the page both ways), Small, Medium, Large (36, 72 and 120 pt, shown as their letter height of about 9, 18 and 30 mm) or another letter height of 3–50 mm, held within 12–200 pt. "Letter height" is Helvetica's capital height; Times and Courier capitals come out somewhat smaller. A fixed size that runs off a page is drawn and reported ("The watermark is larger than page N and is cut off. Choose Auto size or a smaller size.").
- Angle: Diagonal (default; corner to corner of the page as displayed, about 55° on A4 portrait), Horizontal, Vertical, or a custom angle from −90° to 90°.
- Position: centre (default), one of the other eight anchors (top, middle, bottom × left, centre, right; 20 pt, about 7 mm, from the edges), or a point clicked on the preview or typed as a percentage across and down.
- Colour: swatches Black, Grey (default, #808080), Dark red and Dark blue, and "Other…" for any colour; opacity 5–100% (default 25%).
- Layer: **In front** (default) or **Behind** the page. A watermark behind a page is covered by anything opaque on it: behind a scan it cannot be seen at all. When chosen pages are scans, the dialog says "On 2 of the chosen pages (scans) a watermark behind the page cannot be seen. Put it in front to show it there." and Behind stays available. When marks in front meet pages with form fields, those pages are named, because the fields are drawn over marks in front.

**Stamp** (off by default): text VERIFIED, RECEIVED, CHECKED, PAID, ORIGINAL SEEN or custom (1–60 characters, the same characters and tokens as above); size Small, Medium (20 pt, recommended), Large (14, 20 and 32 pt) or another letter height of 2–18 mm, held within 8–72 pt; bold on; colour dark red #A00000; opacity 78% (the owner's numbers); angle 0° (−90° to 90°); position top right (default), another anchor or a point; 20 pt from the edges.

**Logo** (off by default): an image already in the working list (PNG or JPG, added from the computer or the Evidence Vault like any file, so the file limits and the engagement rules apply; WebP, BMP, GIF and one-page TIFF are already PNG after intake), chosen from a list of the list's images and never remembered after the dialog closes **(design call: no path or image is stored)**. Width 18% of the page's displayed width (5–50%, at least 28 pt), height capped at 35% of the displayed height (the owner's numbers); position top left (default), another anchor or a point; 20 pt from the edges; opacity 100% (10–100%, so that a large faint logo can serve as an image watermark). A logo over 1,600 px on its long side is reduced to at most 1,200 px before the run (480 px for the preview); a phone photo's stored rotation is applied; a CMYK JPEG is redrawn in RGB; over 25 megapixels is refused.

**Pages**: all (default), a range from–to, or the first page only, which applies to everything that is on, the watermark included ("Everything that is on, the watermark included, goes on page 1 only").

Marks are placed in the frame of the page as the reader sees it, so they come out right on turned and cropped pages. They are drawn in this order: watermark behind, the page, watermark in front, logo, stamp, each after the page's own drawing is closed off (5.6). Transparency uses a graphics state (`/ca`); the page's own content is not changed; pages that share resources share one copy with the mark's entries added, and the original resources are not changed (about 0.4–0.7 KB a page). Watermark and stamp text is real text: it can be searched and copied, and Redact will see it.

The preview is the library's own output for a one-page copy of the chosen page, so it cannot disagree with the result (within 0.72 pt in the application); it takes about 0.4–0.7 s after a change on a loaded machine. Its expand button opens the viewer with every chosen page drawn marked.

After the run: a watermark behind the page may not be visible (a scan, a picture or a solid background covers it), or may be hidden but this could not be checked (a pattern or a masked picture lies over it); "may be hidden" is an estimate. A page whose own drawing is damaged or cannot be read may have its marks misplaced: the result names the page, and the record gets the flag `markMayBeMisplaced` ("; a mark may be misplaced"). A stamp, logo or text that fits the previewed page but not a later chosen page is refused at Run, naming the page: "The stamp does not fit on page 4. Use shorter text, a smaller size or a smaller distance from the edge. Nothing was added."

Default name `<name>_watermarked.pdf`, or `<name>_stamped.pdf` when only the stamp or logo is on. The result message is "Watermark added to all 5 pages." with the notes above. Record (counts and choices only): summary "Watermark DRAFT, stamp (custom text), logo, all pages" (or "pages 1-12", "page 1"); metadata `pages`, and per part the ready-made text or a template of tokens and punctuation as it is (`DRAFT`, `{client}`), else `custom` with the text's length and the tokens it uses (`watermarkLength`, `watermarkUses`), never the text; font, size, angle, colour, opacity, layer and position; for the logo `logo: true`, its size in pixels, width and opacity, never its file name. `activity.ts` keeps only these keys.

### 5.18 Protect with password (phase 2)

Added by the owner on 14 November 2026. Makes a copy of one PDF that asks for a password when opened ("…; without it, only the number and size of its pages can be seen.").

**Dialog** (`ProtectDialog.tsx`, `protect/`).

- "Password" and "Type it again", side by side, both hidden, with one "Show" / "Hide" button for both. The match is checked as soon as the second field stops being the beginning of the first ("The two passwords match." when it does).
- **Password limits.** 8 characters to 127 bytes: 127 letters, digits and symbols of an English keyboard, fewer of other characters (most Hindi letters count three bytes), because the standard cuts there and some PDF readers refuse longer passwords. The password is used in Unicode normal form NFC. Control characters are refused. A space at the start or end is kept, with the warning "The password starts or ends with a space. It must be typed with that space every time." Characters not on an English keyboard are allowed, with the warning "Some PDF readers cannot open files protected with non-English characters. Letters, digits and symbols on an English keyboard are safest."
- A plain strength hint, never a block: "Weak: use at least 12 characters and mix letters, digits and symbols.", "Fair: mixing in a third kind of character (letters, digits, symbols) makes it strong.", "Strong.".
- Under "Keep the password safe": "If the password is forgotten, nobody can open the protected file, including you. VERA does not keep the password. The unprotected file stays in the list."
- No permission settings: the protected file allows printing, copying and changes once opened (choices are a candidate, section 3).
- The Run button is "Make protected copy"; while it cannot be used it stays focusable and says why ("Type a password of at least 8 characters, then type it again to confirm it.", "The two passwords must be the same."). The result name is under "More options". Above 20 MB the dialog says "This can take a minute for large scans."

**How it is built.** `@cantoo/pdf-lib` 2.11.1, already a dependency and already used to open protected files, encrypts the result with **AES-256** (`/V 5 /R 6`, crypt filter AESV3, strings and streams encrypted, metadata encrypted). The open password and the permissions password are the same (as in the owner's tool). Every permission is granted explicitly: the library's default forbids printing, copying, editing, form filling and accessibility (`/P -3904`); with all permissions given it writes `/P -4`. AES-128 and RC4 are not offered: AES-128 refused non-Latin passwords in the trial, and RC4 is broken.

- **Sealing.** Even saved with object streams, the library left strings readable in the catalog, the page tree, pages, stream and signature dictionaries and objects of generation 1. `protect.ts` seals every such string itself before saving, with a test per kind of place; a file that claims PDF/A-1 is written without object streams with every string sealed. The file is saved once (a second save encrypted it twice).
- **What stays visible without the password.** The password hides every string and stream in the file: all text, form values, comments, bookmark titles, attachments, pictures and the XMP metadata. The file's structure stays visible: the number of pages, their sizes and rotation, font names, image sizes, and the kinds of annotations and attachments.
- **Signed files.** The value of a digital signature is encrypted with everything else, so that the signer's certificate cannot be read without the password. This departs from ISO 32000-2, which leaves it unencrypted **(lead ruling; the owner can override)**. The signature is no longer valid after protecting in any case; some readers then show it as unreadable rather than as changed. The pre-run warning says "This file carries a digital signature. The protected copy will not carry a valid signature: keep the signed original as the evidence."
- **PDF/A files** are protected, not refused, and the result says "This file is marked PDF/A (archival). A password-protected copy cannot be PDF/A; the copy keeps the mark but no longer meets the standard." The XMP is not changed; the record gains `noLongerArchival: true` **(lead ruling)**. The note is shown before the run when the file's uncompressed XMP shows the claim, otherwise after it.

**The check.** The result is opened with the password by VERA's own unlock code and compared with the source object by object, as well as by page count; any difference adds nothing ("The protected file could not be verified. Nothing was added. Try again; if it fails again, restart the application."). Both sides are read with the same library's parser (11a). In a review, pdf.js and six other open-source PDF readers and libraries refused the results without the password and opened them with it; Adobe Acrobat Reader, Microsoft Edge and Google Chrome were not tried (section 9).

**Size and time.** Files over 150 MB are refused before anything is read ("This file is larger than 150 MB, too large to protect in PDF Tools. Compress it or split it into parts, then protect the smaller files."): protecting and checking hold four to five times the file in memory. The run shows three steps with a moving bar: "Step 1 of 3: reading the file…", "Step 2 of 3: protecting it with the password…" and "Step 3 of 3: checking that the copy opens with the password…"; steps 2 and 3 show how far they have got as a percentage. The work reads and writes about 1 MB of objects at a time (up to 1,500 small objects; it was 50), giving the window a turn between slices, so the screen keeps painting and Stop works within each step. Measured in the application at 83–100% CPU: a 320-page text ledger took 21–26 s (146–173 s before the slices were enlarged); earlier, a 52 MB, 40-page scan took 35.7 s in all and a 26 MB scan 18–25 s, with Stop landing within about 0.2–2 s.

**The password** is held only while the tool runs. It is never stored, logged, written to the activity record, shown in a message or error, or kept with the result. Closing the dialog, a change of engagement or user, or the end of the run clears it. The password fields' values are wiped as the fields leave the screen, and after a Stop or a failed run fresh fields replace them, because the screen library otherwise kept the last value in memory after the dialog. A heap search in the application found the password in no DOM node, storage, database, console line or profile file after the dialog closed, and after a Stop and a failed run with the dialog still open.

**The result row.** Marked "Protected" (hint: "Opens only with the password you set. VERA does not keep it."). It is built from the checked copy: thumbnails, the page panel, the bookmark list and the viewer use the unprotected bytes kept with the row in memory (counted in the 300 MB list limit), never the password; those bytes go when the row is removed, the engagement or user changes, or the application closes. Save to computer, the Evidence Vault and the working paper always use the protected bytes; the vault and working-paper dialogs add "This file is password-protected. Reviewers will need the password to open it. VERA does not keep passwords." A protected result cannot be used as input to another tool; the toolbar says "This file is protected by PDF Tools. Use the file it was made from." **(design call: otherwise the password would have to be kept or asked again)**. When a protected file comes back into PDF Tools later (for example from the vault), it is a protected file like any other and asks for its password. The result message is "Protected:" with the result's name, then "It opens only with the password you set. VERA does not keep it. The unprotected original stays in the list."

Default name `<name>_protected.pdf`. Record: "Protected with a password (AES-256)", metadata `{ protection: "AES-256" }` and, for a PDF/A source, `noLongerArchival`; no password, hint or length. A result made from a signed file is marked "Signature no longer valid".

### 5.19 Resize or crop pages (phase 2)

Added by the owner on 15 November 2026 ("make every page of a mixed scan bundle A4, trim margins, add margins"). One tool, on exactly one PDF, in the Organise group after Organise pages (`pageBox.ts`, `pageBoxRun.ts`, `PageBoxDialog.tsx`, `pagebox/`). The dialog says "Make every page of a copy one size, or crop its pages. The original is not changed."

**The dialog.** Two plain choices:

- **Make every page one size** ("A4, or another size you choose."; the default). It opens ready to run: "Resize 7 pages to A4". The size is one drop-down: A4 (210 × 297 mm, default), A3, A5, Letter, Legal, or "Own size (set under More options)". Each page keeps its direction (a landscape page becomes A4 landscape); the content is scaled to fit and centred, never stretched. Small pages keep their size, in the middle of the page ("A receipt stays receipt-sized, in the middle of the page.") **(design call: a 1:1 copy of small evidence is the safer default)**. Pages already that size, within 1 mm, are left exactly as they are; the dialog says how many ("1 page is already A4 and stays as it is."). Under "More options" (closed line "Each page keeps its direction, small pages keep their size, no margin"): the own size (width × height, 10 to 5,080 mm), Direction (keep each page's direction, Recommended; every page portrait; every page landscape), "Do not enlarge small pages" (on, Recommended), a margin around the content (None, Recommended; Narrow 5 mm; Normal 10 mm; another value up to 200 mm; with a margin, pages already that size are fitted inside it too) and the result name.
- **Crop the pages** ("Trim the edges, shown by a frame on the preview."): four boxes in mm, laid out as the page is (10 mm each to start), and a frame on the preview: the mouse drags an edge or the whole frame; each edge is a slider that the arrow keys move (1 mm; Shift: 10 mm; Home: not trimmed; End: as far as it goes), announced ("Left edge: 15 mm trimmed"). Boxes and frame stay in step. The notice "Trimming hides, it does not remove" says "Trimmed parts are hidden, not removed. To remove content, use Redact." **(lead ruling)**. Under "More options" (closed line "The same on every page"): "Swap left and right on even pages" ("For pages printed on both sides."), "Add white space instead of trimming" ("Each page grows by the widths above; nothing is trimmed."; up to 500 mm on each edge) and the result name.

Pages: all, or a range, with the range field and messages of Watermark. The preview shows a chosen page as the run makes it (the library's own call on a one-page copy, drawn by pdf.js), or the page with the crop frame over it, with its size before and after ("This page: 216 × 279 mm (Letter) → 210 × 297 mm (A4)"; "Page 7 is already A4: it stays exactly as it is."); it steps through the chosen pages. The checks before Run use every page's real size, read by pdf.js in its worker; the run checks everything again.

Refusals, at the field and at Run, naming the page: "Trimming that much leaves less than 10 mm of page 8. Use smaller values."; "The margin leaves less than 10 mm for the page content. Use a smaller margin."; "Page 2 would be larger than 5,080 mm, the largest page a PDF can have. Use a smaller margin."; when every chosen page is already the size: "All 3 chosen pages are already A4. Choose another size, add a margin, or choose other pages." At Run a refusal ends "Nothing was added."

**How it is built.**

- Every chosen page is planned before anything changes, on the page as the reader sees it (its visible box, its own rotation and `/UserUnit`), so a refusal names its page and changes nothing.
- Resize: the page's own content is not re-encoded. It is wrapped as marks are (5.16): one scale-and-move, a clip to the page's old visible area, a `q` for each stray `Q`; the original streams unchanged; then what closes it all. The page keeps its own `/Rotate`, so the change is always an upright, uniform scale plus a move, and every coordinate that points into the page moves by the same numbers: comments, links, ink, lines, polygons, callouts, form-field widgets (and the field's text size used when a reader draws the text again, set on the widget so that a field shown on other pages keeps its own), article beads, bookmarks, named destinations, the opening view and every GoTo action (the zoom is left as it was). Border widths scale with the page. Patterns get copies with the same transform. A `/UserUnit` is folded into the scale and dropped: the new page is A4 in real points in every reader.
- Trim: only the page's boxes change (MediaBox = CropBox = the smaller area); the content streams are the source's, byte for byte. **Nothing is removed from the file**: the trimmed parts' text and pictures stay in it; VERA's own viewer no longer shows or reads them, other programs may. A comment, link or form field wholly in a trimmed part is hidden, not removed, and the result says so ("On page 1 a link, comment or form field is now in the trimmed part, hidden but still in the file.").
- Add white space: the boxes grow; the content is clipped to its old visible area, so nothing the page hid before shows in the new margin.
- Every changed page loses its print-production boxes (bleed, trim, art) and its stored thumbnail, because they describe the old page. Everything else is carried: form values, comments, bookmarks, attachments, document properties (Producer becomes "ICAI VERA"; Creator is kept), the XMP metadata, layers, tags. Text stays text.
- Kept and flagged, never kept too little: a page whose drawing closes more than it opens (readers differ on such pages), a page whose drawing cannot be read, an annotation of an unknown kind or one with a measuring scale, a page with viewports, and a pattern that a form without resources of its own would take. The result names the page: "Check page 2: its content could not be read exactly, so it may look different." / "Check page 1: a comment or measurement on it may not have resized exactly."
- A signed file gets the general signed-file warning before the run; the result is marked "Signature no longer valid".

**Result and record.** Default name `<name>_resized.pdf`, `<name>_cropped.pdf` or `<name>_with_margins.pdf`. The message: "7 pages resized to A4; 1 was already A4 and is unchanged.", "8 pages trimmed; the trimmed parts are hidden, not removed.", "Margins added to 8 pages.", then one sentence per thing to check; with nothing to change, "Nothing to change: every chosen page is already A4. Nothing was added." Record (counts and choices only): summary "Resized 7 pages to A4, 1 already A4" ("; 1 page to check" when there is one), or "Trimmed 8 pages: left 15 mm, top 20 mm, right 10 mm, bottom 10 mm, mirrored on even pages"; metadata `mode`, `size` (paper name or "200 × 300 mm"), `direction`, `enlarge`, `marginMm`, or `leftMm`, `topMm`, `rightMm`, `bottomMm`, `mirror`; `pages` ("all" or "2-5"), `changed`, `unchanged`, `pagesToCheck` (`activity.ts` keeps only these). Progress goes page by page ("Resizing page n of N…"), then "Writing the file…"; Stop takes effect between pages.

Measured on a machine shared with other work: the library resized a 500-page mixed file (300 pages changed, 200 already A4) in 1.9 s in Node; in the application 500 pages took 9.6–10.0 s from Run to the result row, and a confirmed Stop ended a 500-page trim in 0.36–0.75 s, adding nothing.

## 6. Where results go

Each result can be sent to any of the three destinations, more than once.

### Save to computer

- **One result**: a save dialog; the file is saved as a PDF (or its own type for images, Excel and Word).
- **Several results**: the user picks a folder once, and each result is saved into it as its own file. An existing file of the same name is never overwritten silently; the new file gets a numbered suffix such as `name (2).pdf`.
- "Save as one zip" is offered as an extra for several results, for emailing. It is never the default.

The row is marked "Saved to computer" only when the save is known to have completed; a cancelled dialog changes nothing. Any file in the list, not only a result, can be saved to the computer; the activity record then reads "Copy of a file from the computer" or "from the Evidence Vault" (and "without its password" for a protected file; ", converted from TIFF to PDF" for a converted TIFF).

The folder window: the user's own Desktop, Documents and Downloads folders, and anything inside them, can be chosen. Any other folder that Chromium treats as restricted (the profile root, AppData, Windows, Program Files) is refused by a listener in `electron/main.cjs`; the pick then ends as "no folder" and a quiet note appears once: "Nothing was saved. No folder was chosen. Windows and program folders cannot be used for saving; choose another folder, such as Desktop or Documents." The note also appears if the folder window ends without a folder for any other reason, and it is withdrawn if a folder is then chosen. Only the latest click's save gives the note, and Save As and zip saves never do. As safety nets: if the save or folder window does not answer within 10 seconds, the Save button is released so that it can be pressed again (the screen is never blocked as a whole); and if the browser refuses to open a second picker, the message "A save window is already open. Finish or close it, then try again. If no save window is open, restart the application." is shown, nothing is saved, nothing is marked, and the file is never silently downloaded instead. Verified with the real folder window in a throw-away probe; the owner is to confirm it through the application (section 9).

If the pickers are not available, the file is sent as an ordinary download. A download cannot tell the application whether it was saved (Electron may show its own Save As window, which can be cancelled). The row's badge then reads "Download started" (hint: "A download was started, because no save dialog was available. PDF Tools cannot tell if it was kept, or where."; phase 1 called it "Sent to download"), and the activity record says "Computer, by download (completion not confirmed)".

How it is built **(design call)**: the application's present downloads cannot tell whether a save completed, and its export channel forces a Word file name. The browser's save-file and folder pickers are used, with the download fallback above. They were found to be present in the development build and when the page loads from `file://`. No main-process save handler was added; the only main-process change is the folder-access listener described above (section 8). The real native windows are not covered by the automated test.

### Add to Evidence Vault

A small form for the ticked results: a name for each (default: the result name), one evidence type for all (the vault's existing five types, default "Document"), and an optional "Workpaper reference". This destination takes results only; a file added from the computer or the vault is already a file the user has, so it is left out and the dialog says how many were left out. With no result ticked, the destination is unavailable and says "Only results can be added to the Evidence Vault from here. Upload originals in the Evidence Vault itself." Saving uses the vault's existing upload path, so the file belongs to the current engagement, is recorded as uploaded by the current user, starts in draft, and appears in the Evidence Vault like any other upload. Files are sent one at a time, with progress and a Stop that finishes the current file. The shared upload code shows its own "File uploaded successfully" message for each file, with no file name.

The row is then marked "In Evidence Vault" (its hint names the vault record). The form warns when this engagement's vault already has a file of the same name, and when the result is already in the vault ("Adding it again keeps a second copy"), but does not block **(design call)**. Names repeated within one batch get " (2)", " (3)".

### Attach to working paper

In this application a working paper attachment is a file on an Audit Execution programme, on one of its sections, or on a working box inside a section, and it always points at a vault file. So this destination saves to the Evidence Vault first (same form as above) and then attaches.

If the result is already in the Evidence Vault, that vault record is attached and no second copy is uploaded. Attaching the same result to a second programme, section or box also reuses the one record. Before reusing a vault record, the application checks that it still exists in the vault list. If it has been deleted in the Evidence Vault screen, the "In Evidence Vault" mark is cleared and the vault form is shown first. Like Add to Evidence Vault, this destination takes results only.

The user picks the programme, then optionally a section, then optionally a box. If the engagement has no audit programme, the option is disabled with an explanation. Sections and boxes marked locked are shown but cannot be chosen **(design call: the main process does not enforce these locks today, and PDF Tools should not be a way to add material to locked work)**.

If the vault save succeeds and the attachment fails, the file stays in the vault and the row is marked "In Evidence Vault". The user is told the attachment failed and can retry it from the same row, or attach from Audit Execution. The vault record is not rolled back, because it is valid evidence.

Existing behaviour to be aware of, unchanged here: in Audit Execution, removing the last attachment that points at a vault file also deletes that vault file.

### File names

A name is cleaned before use: characters the vault rejects (`\ / : * ? " < > |`) are replaced with `_`, trailing dots and spaces are removed, the right extension is ensured (case-insensitive), and an empty name falls back to `document`. Control characters and the line and paragraph separators (U+2028, U+2029) are replaced too. If a name cannot be numbered, it falls back to "result (n)". Names longer than 120 characters are cut in the middle, keeping their start and their end ("…Tax Aud…ith Annexures for AY 2025-26 - final copy v3 revised_pages_1-2.pdf"); a name cut before is cut again at the same place, never with a second "…". A name already in the list gets " (2)", " (3)" without regard to case, as Windows does. The same cleaned name is used for all three destinations.

### Record of what was done

Every send to a destination writes one PDF Tools activity-log entry for the engagement **(design call)**:

- The Audit Trail screen shows only an entry's action, entity and details text. So the details text carries the readable record: operation (for example "Merged 3 files", "Compressed, Balanced", "Compressed to fit 5 MB", "Redacted 14 areas on 3 pages"), destination, source file names with origin, result name, page count, "Still in the file: …" when the result carries comments, attachments or properties (5.1), and the first 12 characters of the result's SHA-256.
- The entry's metadata holds the same facts in structured form, with the full SHA-256, the vault record ids of any vault sources, and `carried` (counts and property names). The screen does not display metadata today and is not changed.
- Passwords and redacted values never appear in either.
- A vault save also produces the vault's own "Uploaded" entry, because the existing upload path is reused unchanged. Two entries for a vault save are accepted.
- The vault stores no hash of its files. The SHA-256 exists only in this log entry; it lets a reviewer check a stored file against what PDF Tools produced.
- A failed log write is reported to the user as a warning; it does not undo the save.
- A result made from earlier results lists its whole chain. The details text reads `Sources: … Earlier steps: <what was done> → <result name>; … (and N earlier steps). Original sources: <name> [vault|computer|result]; …`. The last 10 earlier steps are listed and the rest are counted. The entry's metadata holds `earlierSteps`, `earlierStepsNotListed` and `originalSources`, with the vault record id of each original source that came from the vault. So a vault file that was compressed and then numbered is traceable to the vault record it started from; a redacted, watermarked and protected bundle lists every step.
- Flags, each also a metadata key, with the note the readable summary ends with: `formFieldsDropped` ("; form fields not carried"), `bookmarksDropped` ("; some bookmarks not carried"), `signatureInvalid` ("; signature no longer valid"), `sharedResourcesKept` ("; may still contain images or fonts of left-out pages", for the reasons listed in section 5.3), `protectionRemoved` ("; protection removed", 5.1), `markMayBeMisplaced` ("; a mark may be misplaced", Watermark and Page numbers), `redactedValuesLeftVisible` ("; some chosen values left visible") and `textLayerIncomplete` ("; some text on redacted pages is not searchable").
- Each phase 2 tool's summary and metadata are given in its section: Split into several files (5.3), Compress Fit to a size (5.5), Redact (5.9), Bookmarks (5.10), Organise pages (5.15), Watermark (5.16), Page numbers with header and footer (5.17), Protect with password (5.18), Resize or crop pages (5.19). A Redact, Protect, Resize or crop, Watermark or Page numbers record keeps only the keys its section lists, each of the expected shape; anything else is dropped from the entry, also in the earlier steps of a later result (`activity.ts`). A Redact entry never holds a redacted value, a typed term, a custom replacement token or masked text; a Protect entry never holds the password or anything about it except the algorithm; a Watermark or Page numbers entry never holds a text the user typed, nor the logo's file name. The password boxes of Protect and of the prompt for a protected file share one rule: their values are wiped as they leave the screen.
- If the engagement is changed while an upload is still running, the upload finishes in the engagement it was started for, and its PDF Tools entry is still written there, silently, with that engagement's identity. A file must not exist in the vault without its provenance line. The user sees no message about it.
- Computer saves are logged too: "Destination: Computer.", or "Computer, by download (completion not confirmed)", with ", in one zip file" where that applies.
- Runs whose results are never saved are not recorded **(design call)**.

## 7. Roles, engagement and security

- The tab requires a signed-in user and a selected engagement; that is unchanged.
- Anyone who can open the engagement can use the tools and save to its vault. That is the existing vault rule, enforced in the main process (`electron/sqlite-authorization.cjs`), and this feature adds no path around it.
- Vault input is read through the existing `file-download` channel and vault output through the existing insert and `file-save` channels. Both already refuse other engagements' files.
- Attaching uses the existing `audit_program_attachments` insert. Removing an attachment later remains partner/admin only, as today.
- Switching engagement or signing out clears the file list, results and any held passwords before the new context is shown; with unsaved results the application asks first (section 4). The question is asked by `src/contexts/EngagementContext.tsx` through a guard PDF Tools registers once, beside the list's other module-level protections (`leaveGuard.ts`, `useWorkingList.ts`); it returns no question when nothing is unsaved, and the clearing code itself is unchanged.
- Long-running steps (Redact's finding and rebuilding, Protect, Organise pages, the TIFF conversion, Split into several files) capture the list's context key and session when Run is pressed and check them before every slow step and before adding anything; the Redact dialog's proposals, the page viewer and its Find, and a protected row's unprotected preview bytes are dropped on a change of engagement or user. Redacted values, typed terms, search words and passwords exist only in the dialog's memory while it is open and are never written to the activity log, localStorage, the console or a message that can outlive an engagement switch.
- All processing is local. No tool makes a network request. Phase 2 adds no main-process code, IPC channel, native window, network use or dependency. Its only renderer-side additions of note are a module worker that reads bookmarks off the window thread (5.10) and lazily loaded parts for each phase 2 tool. The application test records the renderer's network requests and reports any made during PDF Tools steps; it tolerates requests for font files to Google Fonts (section 12), which are not made by PDF Tools. Network use by the main process is not observed by it. The lanes' drives found no request from a PDF Tools step; the only requests seen were the application's own font requests to Google Fonts at start-up and when a character outside the loaded font subset was shown.
- The JavaScript engine keeps, process-wide, the last text any regular expression matched. PDF Tools clears it when the engagement or user changes, after every run, when a destination batch settles and when a dialog or the Find box closes, because Redact's patterns and other tools match document text (other parts of the application can leave their own text there; that is outside PDF Tools). The bookmark reader keeps each file's titles in memory while the file is in the list, as thumbnails are kept.
- The only thing phase 2 writes to localStorage is the Redact profile name (5.9). The lanes' drives found no password, typed term, search word or value in the database, profile files, storage or console.

## 11. Known limits (phase 1)

These are limits found while building phase 1. "Not yet verified" means no test or manual check has covered it.

**Phase 1 defects found and fixed during phase 2 (T-048).** They are on `main` since PR #111 and are corrected only by the phase 2 branch (owner decision, 14 November 2026: no separate patch to `main`; the phase 2 pull request states them):

- Page numbers were misplaced (measured 86 pt; 12–333 pt in a reviewer's cases) on pages whose own drawing leaves a graphics state open or a transform in place (5.6).
- Every file opened for drawing pages stayed in memory, about 2.8 MB per opening, until PDF Tools was closed (a pdf.js document was never released after a race in `docOpener.ts`). Fixed and tested: 6 of 6 documents alive before the fix, 0 after; memory flat over 50 viewer open-and-close cycles.
- After Split or Delete pages, a popup on a kept page could keep the text of a left-out comment, and replies kept links to removed comments, because stored null entries were not seen (5.3).
- After Split or Delete pages, a link that went by name to a named destination on a left-out page was kept (5.3).

Some limits below are changed by phase 2: Merge can add and carry bookmarks (5.2); Split and Delete pages carry bookmarks (5.3); the tag "May hold left-out pages' images" reads "May contain traces of removed pages"; files can be reordered inside the Merge dialog; the question before an engagement change (section 4). Phase 2's own limits are in 11a.

### Password-protected files

- Opening a password-protected file runs on the main thread, so the screen is busy while it opens. An 83 MB AES-256 scan took about 18.5 s; typical files take under 2 s. A background worker would remove the wait and is a candidate, left open for the owner. It was not done in phase 1 because of the risk of bundling a worker that must load from `file://`.
- Not yet verified: protected files with no `/ID` entry, and non-Latin passwords on files made by other programs that use the older protection (revision 4 or lower). Linearised protected files are covered in the repository tests only by a hand-built equivalent, not by a real file.
- A linearised file protected with a certificate (public-key) handler may be reported as not protected.
- Opening a file that has only an owner password removes its restrictions in the copy (section 5.1).

### Tools

- Merge does not carry form fields, links between pages or attachments. The merge dialog says so when a chosen file has them. Merge also keeps duplicate hidden page dictionaries (size only) and carries signature marks without a form (the result is marked). Split and Delete pages carry form fields of kept pages but not links by name or signature fields as fields (section 5.3). They are not a redaction tool: fonts shared with kept pages and the form's default resources are copied whole, extra resources are kept when a kept page's text, a string or inline image data contains a resource name, a page whose key holds a `#` that the library cannot read exactly keeps everything, and unknown keys in a layer configuration are copied as they are. In these cases, where the code can tell, the result is marked "May contain traces of removed pages".
- Stop works only between steps for Merge, Page numbers and Images to PDF, and between parts or pages for Split and Delete pages. Reading and writing a very large file are single steps that a Stop waits for; the stop then takes effect and nothing is added (section 5.1).
- Page numbers and Compress keep content from an earlier saved revision of the source that is no longer shown (a PDF can hold older versions of its pages after "incremental" saves). Merge, Split and Delete pages do not.
- Names written with lower-case `#xx` escapes can be re-encoded by the PDF library when it saves, so a page may lose that resource and draw differently. This is rare, and it applies to every tool; Split and Delete pages flag it, Organise pages refuses, the others do not.
- Results were compared with the sources in pdf.js only (the reader PDF Tools itself uses), not in Adobe Acrobat Reader or other readers.
- If a file is such that every page has to be kept whole (the "May contain traces of removed pages" case on every page), Split into Equal parts is as large and as slow as it was before per-page resources were added, and the warning is shown.
- An invisible form field whose only widget is on no page is not carried by Split or Delete pages.
- If the engagement is changed while the folder window is open and a folder is then chosen, the files are still written (the user's own save, started in the engagement it was begun in) but nothing is marked or shown.
- "Signature no longer valid" also appears on a part of a split file that holds no signature. The mark is deliberately cautious.
- Compress: the XMP metadata producer is not updated. Images drawn larger than the page lose more than the nominal dpi. Grey scans without a profile are stored as RGB, so a grey scan can come out slightly larger. Images above 64 megapixels are not recompressed. Compressing a signed file invalidates its signature; the screen warns before the run.
- A file that merely contains the text of a signature byte range (`/ByteRange`) is flagged "Signed". This is a cautious false positive: it adds a warning and blocks nothing.
- Images to PDF is slow for many PNG files (one test run with 200 PNG images of 600 × 800 pixels took 22 s), and the screen shows a busy bar rather than a count. The same image added twice is stored twice in the result. HEIC images are refused (5.7).
- PDF to images: the size shown before the run is an estimate and a warning only. The 300 MB working-list limit is enforced on the real bytes during the run, and a run that would exceed it stops and adds nothing. Very large pages are drawn at a reduced dpi, and the screen says so. Out-of-memory and renderer-restart failures have their own messages; these are proven by unit tests, or by a provoked restart, not by a natural failure.
- The working list holds at most 300 MB and warns at 150 MB (section 5.14).
- The largest sizes have not been run by anyone: a 300 MB list, a 300 MB merge, a 500-page PDF to images at 300 dpi, 200 images in one Images to PDF, and a 150 MB upload to the vault. Several steps copy the bytes more than once, so the figures are design limits, not measured ones.

### Screen and records

- When the engagement changes while the PDF Tools screen is closed, the working list is cleared by a watcher within about one second, not instantly. Until then the files stay in memory but are not shown. (Phase 2's change to `src/contexts/EngagementContext.tsx` adds the question of section 4; it does not make the clearing immediate.)
- A message naming a file (for example "result made", "not added") can stay on screen for a few seconds after an engagement switch. It is the same user and nothing can be done with it.
- The "In Evidence Vault" mark can be out of date until the next destination dialog is opened, if the record is deleted in the Evidence Vault screen. Attaching rechecks the record (section 6).
- There is no warning when the application is closed while results are "Not saved". A warning needs a change to the main process (`electron/main.cjs`) that interacts with the automatic update's restart; it was not made in phase 2 either.
- Opening PDF Tools loads up to 500 activity-log rows of the shared hook (the hook's own limit), although only its write function is used. The shared upload hook shows its own "File uploaded successfully" message for each file, without a file name, even after an engagement switch.
- The Evidence Vault picker list is not virtualised, so a vault with hundreds of files may be slow to scroll.
- Both PDF libraries are packed whole into the installer, although the screen's code already holds what it uses, and `public/pdf-tools` is packed twice. This adds to the installer size only.

### Not checked by the automated test

- Native save and folder dialogs cannot be driven by the automated application test, which replaces them with stand-ins, and are checked by hand, as are dragging files in from the desktop and a screen-reader pass. This is not theoretical: on 14 November 2026 the owner's hand check found that saving to a folder failed with "A save window is already open", after automated verification had passed (cause and fix: section 6). Choosing Desktop, Documents and Downloads themselves is accepted and was verified with the real folder window in a throw-away probe; the same through the application screen, and the single-file Save As window into those folders, are not yet verified.

The package was not installed and not published, and the installer was not run.
- Network use by the main process, and by a packaged application at start-up (it checks its update feed), is not observed by the application test.
- Rendering of JPEG 2000, JBIG2, CMYK and CJK-font PDFs from `file://` with a real file; dark theme; Hindi or other non-Latin file names end to end; a file whose full path is longer than 260 characters (in a review such a file was not added and nothing was said; whether the browser's file input or PDF Tools drops it needs a check with the real Windows file window).

### Redact

Redact is switched on at revision 8. These limits describe the tool as built after fix waves 5 and 6.

- No separate independent test ran after fix waves 5 and 6: on the owner's instruction of 16 November 2026 Redact was switched on and checked with the whole module in one final pass (5.9). Tests 1 to 5 found, in order, 8 survivors, 8 survivors, 8 blocking findings, 14 blocking findings and 4 blocking items; all were fixed.
- Test 5's planned new cases on unusual PDF structures against the newest protections (text positions proved against the page's pixels; the rule for when a page may be copied unchanged) were not built. Those protections rest on the 342 earlier cases run again (324 held, 7 refused safely, 11 left the value, all 11 stated limits), on the build lanes' own tests and on the ordinary-document tests.
- The limits the dialog itself states stand (5.9, "What it cannot see"): text inside pictures, barcodes, QR codes and scanned pages; letters drawn as shapes; a stamp set to print but not to show on screen; a value split between two table cells or two columns; a word broken at a line end without a hyphen; text in a font that shows one letter and gives another when copied. The 11 cases that left a value in test 5 were all of these kinds.
- Not findable at all: text drawn as pictures or outlines (scans, outlined text, a Type 3 glyph that draws the value as outlines only); text whose font has no usable character map, or one whose map gives other plausible letters with no glyph names to compare; characters written out of reading order; a value split by other text in reading order (two columns). Encoded copies of a value (base64, reversed text) in links and comments are not looked for. Only boxes the user draws remove such text.
- A value is found the first time only in a form the patterns know; some forms are found only when the same value is also written plainly elsewhere (a code wrapped over two lines, a dotted code, an email with a space before `@`, a percent-encoded value). A typed name glued to the word before it is not found (a name broken by a hyphen at a line end is found). Look-alike letters from another alphabet and Devanagari digits are not read as the value. Old-format voter IDs and driving licences, a demat client ID written apart from its DP ID, and a BSR code and challan serial with words between them are not found. The UPI handle list is a fixed list: a new bank handle is "possible", not missed.
- Boxes may cover more than the value: up to a word or two on letter-spaced lines and in fonts far from Arial; a box that cannot be closed is widened to the whole line (in one all-kinds test file, 216 of 707 boxes); a watermark pattern tiled over a page is covered tile by tile; text or a drawing that cannot be read on a rebuilt page is covered whole (bullets in a symbol font with no character map are boxed). Two drawings compared at the run's resolution join a mark smaller than one 6 px cell next to a box to it. There is no shrink control: untick and draw instead.
- In the searchable form, every word next to a redacted value leaves the text layer (the box padding and the word padding together exceed an ordinary space): the text stays visible in the picture but cannot be searched there. Hindi, the rupee sign and other characters outside Windows Latin-1 are left out of the text layer of redacted pages; the note names Hindi only where the redacted pages have Hindi, and otherwise speaks of "some scripts and symbols".
- A redacted page becomes a picture at 150, 200 or 300 dpi: softer than the original when zoomed past that, and larger. Comments, links and form fields on a redacted page become part of its picture: links there stop working and fields there can no longer be filled in. Pages copied unchanged lose attachments in comments, media, scripts, page actions, private application data, XMP metadata and thumbnails; the document loses its properties, XMP, attachments, scripts, named destinations, page labels, tags and article threads. Information inside images on unchanged pages (for example a photo's camera data) is not removed.
- A signed report whose signature dictionary or certificate holds a typed name asks "Flatten this page?" on every run; answering yes is safe.
- A 10-digit mobile number written with no prefix, label or grouping, an unlabelled IP address, and a name or address without a label are not proposed; type them in. A name or address after a label is only ever proposed unticked: the tool cannot tell a person from a firm.
- Time: the proof draws each rebuilt page twice more and reads every page once more; a 10-page statement with a PAN on every page took 7.0–7.7 s in Node and 9–11 s in the application at revision 6 (the application reopens each copy of the file for every page; a second renderer document would save about 0.5 s on 20 pages, section 3). At revision 5, before the fix waves, a 200-page statement took 89.6 s to search and 314 s to redact on a loaded machine, giving 41.1 MB, with the renderer at 873 MB. A test file of 28 pages with 707 areas took 209 s as Searchable and 41 s as Picture only in Node.
- A value split by a page turn is not joined: when more than four lines of other text stand between its halves; when a half is longer than about 64 characters or three lines and lines must be left out to join it; when the value's own line is taken for a row that the next page repeats; or when the lines to leave out are not next to the turn in drawing order (columns are the only reading by position). A PAN or an account number that stands nowhere whole, only across a page turn, is not found: the rule for a value with no whole mention is for typed words only.
- A typed value where letters cannot be read: one unreadable glyph stands for at most three letters inside one word; a space the text reader puts inside a word is not bridged; a typed value with under a third of its letters readable, or in a script outside the 16 the code lists, gets no place of its own. The unreadable text of its script is then covered whole on the pages being redacted, which blacks out more than was asked (on the test letter 10.4% of the page against 2.7% asked). Devanagari digits are not read as a number.
- Account and card numbers: where the end of a number is uncertain the list shows the shorter number (9 to 16 digits) and the digits after it are covered, so two account numbers that share those first digits appear as one value and are covered together. The covered area also takes a short figure written right after the number (a count before "EMIs", a footnote mark, the figure that starts the next line: 2 places, one digit each, on 140 test documents). A date joined to an account number by a hyphen right after its label is not read as a labelled account.
- Labels not read: the second line of a name wrapped in its table cell under a column heading (on one test document 286 px of two surnames stayed visible under the DPDP profile); wrapped column headings other than "Date of / Birth"; an account column with no IFSC beside it under a two-row heading; an addressee after a designation line when the name has no title; a name after a label in an Indian script; a "Name" heading wrapped in its cell; tables whose empty cells shift the cell position; the letter-spaced label "A A D H A A R". Text of a link address can be offered as a possible name.
- Slanted text: boxes are upright rectangles, so a slanted watermark over a page is covered whole when a chosen value stands at a slant in it (on the one-page test statement about 61% of the page went black against 40% asked). Three ordinary test documents get more black than the values need (11.1% against 2.7%, 9.7% against 2.7%, 9.9% against 5.6% of a page); the cause was not traced.
- Window holds on a 500-page statement, measured in test 5 and not paced since: four later steps hold the window 0.4–0.8 s each ("Checking" up to 0.79 s, "Putting together" up to 0.65 s, "Drawing" up to 0.59 s, saving up to 0.37 s). Placing every value on a dense register page takes several seconds, in turns (slow, not a hold). The final pass's own figures are in 5.9 ("Switch-on").
- Found in the final pass of 16 November 2026 and left as they are: on the two-page salary register under Balanced, drawing the review list holds the window about 0.6 s; on a 500-page statement "Checking…" still holds up to 0.71 s after its fix (one 256 KB reading is itself a 0.35–0.5 s stretch; a smaller reading is a next task); typing a full name does not cover the surname standing alone elsewhere ("Dear Shri …,"), so the surname has to be typed too; on a page labelled only in other Indian scripts the mobile and account number are not ticked by the find and have to be typed or boxed; on one test document a name that was not chosen, beside a widened box, stayed visible in the picture but lost its searchable text (cause not traced).

### Bookmarks

- A bookmark whose page is left out by Split, Delete pages or Organise pages is dropped even when bookmarks under it are kept (they move up a level), so a chapter heading can disappear while its sections remain (lead ruling, 5.10).
- Bookmarks that open other files, launch something or run a script are not kept by any tool that rewrites bookmarks; nor are links from a bookmark to a structure element.
- A file with more than 10,000 bookmarks or deeper than 32 levels cannot be edited with the Bookmarks tool, and the other tools carry none of its bookmarks. The 10,000 and 32 limits were chosen, not measured against real documents.
- Saving 500 pages with 2,000 bookmarks took 13.6–17.1 s on the window thread on a loaded machine, with Stop between the save and the check only. The reading worker carries its own copy of pdf-lib (a 526 KB part of the build). Titles are cleaned when read, so a rewrite also tidies the file's own titles (spaces collapsed).
- A merge whose sources together hold more than 10,000 bookmarks keeps the per-file bookmarks and leaves out whole sources that do not fit, counted in the note.

### Page viewer and Find

- No text selection or copy, and no side-by-side comparison; very large zoom on a large page is drawn at reduced sharpness (16 megapixel cap).
- The first sharp drawing of a 300 dpi scan page takes 2.3–3.0 s (the enlarged thumbnail is shown meanwhile). After the page renderer stops answering, pages come back after about 31–35 s; closing and reopening does not speed this up. All drawing (viewer, thumbnails, tool runs) shares one worker.
- A page that pdf.js draws only in part gets no note. "Blank page" also appears on pages that are blank on purpose.
- Opened from Organise pages, the viewer shows the page as it is in the file, not with the planned rotation, and numbers pages in file order. The viewer's own buttons still say "Turn the view left/right" (it turns the view only).
- After a control turns itself off, its tooltip shows the reason again only once the pointer has left it (the reason is always available to screen readers).
- Find: Hindi that a file stores in the order it is drawn (some PDF writers put the vowel sign ि before its consonant, or store some vowel signs with no character at all) is only partly found; files that store Hindi in reading order match fully. Text is searched in the order the file stores it, so a phrase drawn in pieces out of reading order, or across columns, may not be found. Inside a piece of text, character positions are estimated from a similar system font, so in a very different font a highlight can be a little off inside a long line (the line's extent is exact); vertical writing highlights the whole piece. Scans have no text until OCR (phase 3). Reading a 320-page ledger took 10–11.4 s at 100% CPU, to be re-timed on an office laptop. Up to about 24 MB of page text is kept while the box is open.

### Organise pages

- Moving a page in a 300-page file took about 85–110 ms per key press on a loaded machine; dragging works within the 200 tiles shown.
- "· was N" appears on every tile whose number changed, so removing page 1 marks every later tile.
- The activity log cuts the summary at 120 characters, which can cut the library's sentence about what was not kept; the result's record and the `notCarried` metadata keep it whole.
- The page check covers page content and the forms it draws, not patterns, Type 3 glyphs or comment appearances. A name holding a real `#` followed by a lower-case hex pair in one of those places can lose its image when the file also has a genuine lower-case escape.
- A run that both moves and rotates saves twice (about 1.6 s more on 300 pages).

### Watermark, stamp, logo, and Page numbers with header and footer

- Text uses the standard PDF fonts: Latin characters only (Windows Latin-1); Hindi and ₹ are refused with a sentence (section 3, candidates). A watermark behind a scanned page cannot be seen. A mark in front is painted under form fields and comments, which may cover part of it.
- "May be hidden behind" is an estimate from the page's own drawing (clip paths, shadings, fills and masked pictures are read; overlapping covers are added up).
- A stamp, logo, header or footer that fits the previewed page but not a later chosen page is refused only at Run, naming the page.
- The preview takes about 0.4–0.7 s after a change on a loaded machine.
- "Letter height" in mm is Helvetica's capital height: Times and Courier come out smaller than the mm typed.
- On `/UserUnit` pages, sizes and margins are real points; phase 1 page numbers on such pages move (deliberate). Pages whose drawing is damaged or uses filters the library cannot read with certainty may be misplaced; they are flagged. Two filters (`/A85`, `/LZW`) are handled by reasoning only, without a test file.
- CMYK JPEG logos are redrawn by the browser's decoder; this was reasoned, not run with a CMYK file in the application.
- Typing ₹, or any character outside the loaded font subset, into a field can make the application request a font from Google Fonts (section 12).

### Protect with password

- It runs on the screen's main thread in slices: a 52 MB scan took 35.7 s in all on a loaded machine, 26 MB took 18–25 s, and a 320-page text ledger 21–26 s. Files over 150 MB are refused. A forgotten password cannot be recovered. A protected result cannot be used as input to another tool.
- The check reads the source and the result with the same library's parser, so a misreading of the source by that parser would be carried into the copy unnoticed (an independent parser found none on 8 files).
- Content that only earlier saved revisions hold is kept, encrypted, and comes back after unlocking.
- The file's structure is visible without the password (5.18). A signed file's signature value is encrypted, which departs from the standard. A PDF/A file is no longer archival once protected.
- While the dialog is open the password is in the screen's state and in the field's value attribute; "Show" turns the fields into plain text for the operating system's input services. A copy of the last full value typed may stay in the browser engine's own memory, where JavaScript cannot reach or erase it (seen once in a heap snapshot, as for any typed text). Stop during the unlocking part of the check is not pinned by a test.
- Non-English passwords: readers differ (in the trial, one reader refused passwords over 127 bytes and another refused an accented letter); the dialog warns; Adobe Acrobat Reader, Microsoft Edge and Google Chrome are still to be tried.

### Resize or crop pages

- Trimming hides, it does not remove (lead ruling, said in the dialog and the result message): VERA's own viewer no longer shows or extracts the trimmed text; other programs may.
- Structure (accessibility) layout boxes are not moved. A page whose drawing closes more than it opens, or cannot be read, is resized safely (nothing escapes the new layout) but flagged "Check page N", because readers differ on such pages. Pages with viewports or measuring scales are flagged.
- One crop for all chosen pages (with the even-page swap). There is no large view of the crop frame (the preview is about 300 px high so that the dialog fits 1280 × 720); the boxes give exact values.
- A field's text size is scaled on the widget, which strict readers may ignore for fields with several widgets. The page sizes for the counts before Run are read by pdf.js; if that read fails, the dialog counts nothing and the run still checks every page. The whole file is saved again by pdf-lib (as every tool does); pages already the size keep their dictionary and content byte for byte, not the file.

### Split into several files

- At bookmarks uses the main bookmarks only: a file with one main bookmark and its chapters under it gives one file (choosing the level is a candidate, section 3).
- The files of a split into ranges or at bookmarks are grouped in the list as "(first name) and N more" (parts of Equal parts keep "(name) — N parts").
- Each file holds the fonts its pages use; a ledger with an embedded font split into ten files takes about twice its own size in all.

### Compress, Fit to a size

- A search is four passes over the images (plus one quick re-save), each about as long as one level: about 40–60 s for a 20-page 300 dpi colour scan on a loaded machine, and about 12 minutes for a 300-page, 158 MB scan (one Balanced pass alone: 4.6 minutes). Every pass can be stopped.
- The ladder's steps are about 10–30% apart (wider at the top), so a result is usually within about a quarter under the size asked; a generous size on a 300–400 dpi scan can come out well under it.
- The search holds the parsed document, its first re-save and at most two results: about three to four times the file.
- A grey image with its own profile is written as plain RGB when the browser's encoder writes three components (it always does), so the grey profile is not applied. CMYK, Lab, palette, Separation, DeviceN and masked images are not reduced by any level. Not run on a real grey-profiled or CalRGB scan from a scanner.
- There is no size estimate before the run. Keeping or removing a result that does not fit is the result row and its message, not a question in the dialog.
- The level's or size's part of a long default name is kept by cutting the name's stem at its end, not in the middle as other default names are cut (`compressFit.ts`).

### TIFF

- A TIFF whose strips together claim more bytes than the file holds (corrupt byte counts) is refused as damaged; a file holds at most 4,000,000 strips or tiles and 500,000 directory entries, and directories that overlap or loop end the file as damaged.
- Formats and sizes outside 5.7 and 5.14 are refused with a sentence; old-style JPEG, common in some old fax archives, is refused. A TIFF whose strips overstate their byte counts past the end of the file is read when the data itself is whole.
- Fax pages are stored as decoded 1-bit pictures: on the synthetic text page that is 0.55 times the size of the Group 4 data, on a noisy page 0.77 times; on real scans Group 4 may be smaller (size only).
- pdf.js 5.4.296 draws the last row of a 1-bit picture only in part (up to 7 pixels short), so each converted 1-bit page is stored with one more white row just below the page's bottom edge, which the page box cuts off. Scanned PDFs from elsewhere still show this pdf.js limit in the application, invisible in practice.
- Not tried with a real scanner or portal TIFF, nor in other readers.

### All phase 2 tools

- A deliberately built PDF can hold the window for some seconds while it is read, because pdf-lib's own reading is not split finer than its waits (on a loaded machine an 8 MB file with a stream that never ends took 9 s, and 75,000 tiny objects 39 s); nothing leaks and nothing is lost. Reading added files in a background worker would remove this (section 3).
- Merge and Organise pages (moving pages) hold the window about 0.6 s inside pdf-lib's writer on a 320-page file; it cannot be sliced without replacing the writer.
- Images to PDF holds the window about 0.3 s per picture while pdf-lib turns it into the PDF's picture (section 3).
- A vault file over the size limit is read before it is refused; refusing it earlier needs a size check in the main process.
- Stop lands at the end of the step, not during the read, in Compress, intake, Images to PDF, TIFF, Protect and unlock, and in Organise pages' final check.
- Bookmarks, Watermark, Page numbers with header and footer, Protect with password and Resize or crop pages re-save the source as it is, so, like Page numbers and Compress in phase 1, they keep content of earlier saved revisions; Redact, Organise pages, Split, Delete pages and Merge do not.
- Names written with lower-case `#xx` escapes: Split, Delete pages, Merge, Page numbers, Watermark, Compress, Bookmarks, Resize or crop pages and Redact's copied pages can lose an image or font named that way (as in phase 1, 11). Organise pages checks every page and refuses instead. A general fix is a candidate (section 3).
- The carried-content sentence counts comments with text, attachments and filled properties; it does not look for hidden or white text, form values, or XMP fields other than title, creator, description and keywords.
- Results were compared in pdf.js, and by reviewers in other open-source readers; not in Adobe Acrobat Reader, Microsoft Edge or Google Chrome.
- Every screen was driven in the real application by its build lane on scratch production builds; the repository's own application test is in section 9. Timings were taken on a machine at full load from parallel work (and it slept several times during the lanes), so they are upper bounds, not performance measures.
- The dark theme's low contrast in dialog text (section 12); the loading outline is very faint in the dark theme.

## 12. Outside this feature, for the owner

These are problems in the application that were found while building PDF Tools. They are not caused by it and **none has been changed**. They are listed for the owner to decide.

- `src/index.css` imports the Inter font from Google Fonts. Displaying a character outside the font subset already loaded, for example the rupee sign, can cause a font request to `fonts.gstatic.com`. No file content is sent, but this conflicts with the "no network" aim of section 7. A fix is to host the font inside the application, which edits a shared file.
- The main process does not enforce section and box locks on working-paper attachments, so Audit Execution lets users attach to locked items. PDF Tools is stricter: it does not offer locked sections or boxes.
- Deleting an Evidence Vault record leaves Audit Execution attachments pointing at it.
- `uploadFile` in the Evidence Vault hook inserts the database row before it writes the file, so quitting in between leaves a record with no file, and it shows the raw error text of the main process to the user.
- A stray "0" appears next to each file on the Evidence Vault screen and in each section header of Audit Execution (a flag stored as 0 is printed).
- The Audit Trail Details column cuts long entries at the right edge (about 45 characters at 1280 px width), so the sources, destination and SHA-256 of a PDF Tools entry need horizontal scrolling. The full text is in the record.
- The application has no `will-download` handler, so a download opens Electron's own Save As window.
- Deep links of the form `?tab=` on VERA Tools bounced to another tab in some cases (on `a15b4c3` VERA Tools follows `?tab=` only when it changes).
- The header update button overlaps the engagement switcher at 1280 px width.
- The packaged application checks its update feed at start-up.
- `AuthContext.tsx` writes the signed-in user's id to the console at sign-in.
- An automated security check flagged a possible stored cross-site-scripting problem in `public/caat/caat-tools.html` (CAAT Tools, T-024): values from a saved workspace or shared mapping profile are put into the page without escaping. This was not verified by us and is not part of PDF Tools.

Found while building phase 2 (T-048); none has been changed:

- **Audit Trail times are shown 5½ hours behind IST** ("14 Nov 2026 19:01" for an action at 00:31 IST on 15 November), and "Today's activity" read 0. The owner decided on 15 November 2026 that nothing changes there; it is listed here only.
- The Google Fonts request is wider than said above: the application fetches its fonts (Inter, JetBrains Mono) from `fonts.googleapis.com` and `fonts.gstatic.com` at every start-up, before PDF Tools opens, and any character of another subset shown anywhere (other currency signs, accented, Cyrillic or Greek letters) triggers a further request. Hindi and emoji did not.
- PostHog analytics (`posthog-js`) is in the bundle and is initialised when the Feedback page is opened, with automatic capture off but session recording not explicitly disabled. If session replay were ever enabled for the project, the rest of the session (PDF Tools file names and thumbnails included) could be recorded. Setting `disable_session_recording: true` would rule it out.
- Electron's own menu keys act behind every dialog: Ctrl+R reloads the window and Ctrl+W closes it, even with a PDF Tools dialog or the viewer open (unsaved results are then lost).
- Closing VERA with results not saved gives no warning. A question needs about 9 lines in `electron/main.cjs` plus a listener in PDF Tools, and must be tested with the automatic update's restart, which a cancelled close would hold up.
- Ctrl+Y ("My Tasks") goes to `/my-dashboard`, which has no route: the 404 page logs an error. Ctrl+B is both "Financial Statement Review" and the sidebar's fold.
- The application's dark theme leaves titles, labels, file names and Close low in contrast in the tool dialogs (phase 1 dialogs too); `--destructive` and `--warning` have no dark values, and the newer `--*-soft` badge tokens have no dark values either, so PDF Tools did not adopt them.
- The GST validator `isValidGstin` refuses state code 38 (Ladakh) and codes 96 and 99 (5.9); whether that is right is legal content for the owner to check.
- From the UX audit, application-wide: the header's build label, search box, update button and engagement switcher overlap at 1280 px and even at 1920 px; the sidebar brand reads "AuditPro / Audit Management" and its title is hard to see in the light theme; the header search box looks usable but is not wired up; two toast systems are mounted; the shared status badge's amber text measures 2.4:1; working-paper wording differs between screens ("Workpaper Ref", "WP Ref", "working paper"); the VERA Tools page header and tabs take about 175 px of height.
- With DevTools attached and its Page domain on, Chromium makes `window.confirm` return true at once, so any test driven that way can never answer Cancel to a question; it must stand the question in (section 9).

## 13. Inputs from the owner's earlier tools (14 November 2026)

The owner offered two desktop tools of his own as input for the whole of PDF Tools, every phase ("a suggestion, not a compulsion"): "PDF Redact Pro" and "PDF Manager Pro", both written in Python with PyMuPDF and PyQt5. Their code was read; their sample documents were not opened. The owner deletes both folders after this study, so this section is the record. Only behaviour, rules and numbers transfer, not code: PyMuPDF and Ghostscript are AGPL-licensed (and PyMuPDF is Python), so neither can be bundled into this application.

### How the earlier tools map to PDF Tools

| Earlier tool feature | PDF Tools |

| Extra page-number styles (roman, alphabet, circles, "Pg-1", "1.") | Phase 2, 5.17 |

What phase 2 took from them, and where it chose differently, is said in each section: Redact's categories, profiles, every-occurrence search, joining of boxes, the 95% safety rule, the review list, typed terms with a reason, the `[REDACTED]` token, metadata and attachment removal (always on in PDF Tools, optional in his tool), and counts by reason in the record (5.9; padding 1.5 pt instead of 1 pt; mobile, IP address, name and address rules narrowed after measuring false matches; the text under a box is turned into a picture instead of being removed from the page, because his method needs PyMuPDF); the watermark, stamp and logo numbers (5.16); the header and footer tokens and styles (5.17; margin kept at phase 1's 28 pt; circles drawn lighter); AES-256 with one password (5.18; all permissions granted explicitly).

### His pipeline

PDF Manager Pro applies every tool the user switches on to every output page in one run, in a fixed order: watermark behind, page content, watermark in front, page number, header, footer, stamp and logo, page rotation; then compression; then the password; then conversion. Merge, split and batch are only different ways of choosing which pages go through. PDF Tools runs one tool at a time and keeps the chain of steps in its record; a saved preset of several steps is a candidate (section 3). Watermark (5.16) keeps his drawing order.

### Numbers kept for later work

- Compression levels Low, Medium and High: target resolution from the input scan's own resolution (input 300 dpi or more: 200, 150, 100 dpi; 200–299: 150, 100, 72; 150–199: 150, 100, 72; below 150: 100, 100, 72); JPEG quality 85, 60–65 and 30–45; images under 80 px skipped; fonts subset; High also removes XML metadata. Ghostscript was used when installed, PyMuPDF otherwise.
- Page ranges `1-3,5,7-9`; empty means all; out-of-range values clamped and bad parts ignored silently (PDF Tools reports them instead).
- Page numbers: 9 positions, 20 pt padding (10 pt at the bottom).
- Convert to images: PNG at 144 dpi, `page_0001.png`.

### Phase 3 design inputs

**PDF to Excel** (one worksheet per page, named `Page_n`):

1. Tables found from the page's ruling lines (his settings: lines strategy, intersection tolerance 8, snap tolerance 4, join tolerance 4), each table written as rows.
2. If a page has no ruled table: words grouped into rows when their tops are within 4 pt; column starts found by clustering the words' start positions at 18 pt, the cluster width widened by 6 pt at a time until there are at most 80 columns; each word goes to the nearest column start; words that land in the same cell are joined with a space; empty cells at the end of a row are trimmed.
3. If that gives nothing: the page's text in cell A1.
4. Columns sized to their content.
Phase 3 (5.11) adds what his tool did not: numbers written as numbers, Indian digit grouping understood, and a preview before saving.

**PDF to Word**: a layout-preserving converter first; if the page needs recognition, paragraphs of recognised text with a page break per page ("[No text detected]" for an empty page); as a last resort, each page as an image. No layout-preserving converter is available in this application's stack; phase 3 must choose one or design without it.

**OCR**: a page counts as scanned when it has fewer than 20 characters of text ("auto"), or every page is recognised ("force"); a language setting (default English) and a resolution from 72 to 300 dpi; recognised words grouped by block, paragraph and line into rows for Excel (his engine's page segmentation mode 6). In his redaction tool, pages were rendered at 3×, words above a confidence threshold matched whole against the same patterns, and boxed with 3 pt horizontal and 2 pt vertical padding. Phase 2's Redact takes words with their positions, so recognised words can feed it the same way.
