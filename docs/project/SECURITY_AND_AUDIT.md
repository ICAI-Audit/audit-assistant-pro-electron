# Security and audit controls

This is a code-grounded control review with an isolated runtime regression harness. It is not a penetration test, privacy-law opinion or security certification. T-003 did not change production authorization rules or implement finalization.

## Active IPC path

- `electron/main.cjs` calls `registerIpcHandlers()` after Electron is ready and creates a `BrowserWindow` with `electron/preload.cjs`.
- `electron/preload.cjs` exposes `electronAPI.sqliteAuth`, `sqliteGetCurrentUser`, `sqliteQuery`, file operations and export through `ipcRenderer.invoke`.
- `sqlite-auth` maintains a module-global `currentUserId`; login/signup set it and logout clears it. `sqlite-query` does not consult the session, IPC sender, user role, or `AccessControl`.
- `getSqliteDb()` opens `audit_assistant.db` under `app.getPath('userData')` and initializes schema/migrations on the first database call. The T-003 entry shim verifies and sets a fresh temporary profile before it requires `main.cjs`; its marker confirms the database is absent before production code is loaded.
- Search of the active main and preload found no import or call of `sqlite/access-control.ts`. That helper is not active enforcement.

## T-003 control matrix

The command `npm run test:t003-authorization` builds the renderer, starts the actual Electron main/preload handlers with a synthetic profile, and invokes the exposed APIs using CDP. The test deliberately preserves assertions for required denials. It exited non-zero with 14 failing behavioral assertions and 5 passing setup/observation assertions (Node reports the enclosing test failure as an additional failure). All account, engagement, evidence and file data was synthetic and temporary.

### Helper limitations even if connected

- `sqlite/access-control.ts` defines `Role` as `partner | manager | senior | staff`, but `user_roles` schema accepts `admin`, `viewer` and `user` as well. The helper does not define their privileges.
- `checkEngagementBasedAccess` calls `getEngagementIdForRecord(table,id)`, which selects only an `engagement_id` column and returns `null` on failure. `evidence_links` has `procedure_id` and `evidence_id`, not `engagement_id`; the helper therefore cannot derive either related engagement. `filterResults` does not include `evidence_links`.
- The helper does not enforce allowed columns, protected-field changes, evidence approval/lock transitions, or no-filter bulk mutation limits.
- Wiring `AccessControl` alone is not sufficient. The active bridge must authenticate the caller, validate the table/action/columns, derive ownership for related rows, constrain both read and write queries, and bind file operations to metadata.

## Prioritised remediation proposal

This proposal is not authorization to change production rules. Each implementation needs a separately scoped task, regression tests and review.

| Priority | Affected handlers / proposed remediation | Compatibility risks | Required product decisions |
| --- | --- | --- | --- |
| P0 | `sqlite-query`, `file-save`, `file-get-path`, `file-download`, `file-delete`: reject protected calls without an authenticated principal; bind the principal to the invoking `webContents` and validate the sender/frame. Keep only the explicit signup/login path usable before authentication. Revoke that sender's session on logout. | Existing renderer initialization and auth flows may call database methods before sign-in; account for first-user signup, app reloads and any multiple-window behavior. A module-global user ID cannot safely distinguish simultaneous renderer sessions. | Is authentication local-device-only or multi-user per window? Can any renderer route invoke signup, and when is the first admin established? |
| P1 | `sqlite-query` select/insert/upsert/update/delete: connect an approved policy layer; allowlist tables, actions and columns; enforce record/engagement assignment in query predicates and preflight checks; protect role and identity columns; deny unfiltered writes by default and cap approved bulk operations. | Renderer uses a Supabase-like generic query API across many tables. Existing unfiltered list/lookup and import flows may depend on wide access; add an inventory and migrate call sites instead of silently breaking them. | Define admin/partner/manager/senior/staff/viewer/user privileges, firm-wide vs assigned lists, engagement creation, global reference tables and permitted bulk behavior. |
| P1 | `evidence_links` insert/select/update/delete and related evidence/procedure handlers: derive both sides' engagement IDs; reject cross-engagement links; filter list results through both relationships. | Existing links may already cross boundaries; do not silently relink or delete records. Detect and report inconsistent rows for owner-directed remediation. | Are shared or reused evidence files across engagements allowed? If so, define explicit sharing and audit rules. |
| P1 | `file-save`, `file-get-path`, `file-download`, `file-delete`: resolve an authorized evidence metadata ID to a canonical stored path in main; do not trust renderer-provided bucket/path as authorization. | Existing `file_path` values and bucket conventions may not be uniform; missing/orphaned metadata and legacy file layout need a migration/compatibility inventory. Preserve file bytes and report orphan handling. | Define file sharing, retention, export/download roles and recovery behavior. |
| P2 | Evidence update/approval handlers: enforce immutable fields and allowed transitions for draft, prepared, reviewed, approved, locked and reopened states, with actor/reason history. Keep whole-file lock and completion out of this task. | Current screens may edit records after review; enforce server-side and update UI affordances together. Existing unlocked/approved rows need careful compatibility handling. | Who can prepare, review, approve, lock, reopen and unlock; what reason/history is required; which evidence changes invalidate approval? |
| P2 | `app:exportFile` and `app:openPath`: define session, engagement, report-state and path policy; retain expected draft-export workflows while preventing unauthorized use. | Exports are generated in renderer memory and may be needed offline; a strict sign-in requirement could disrupt a documented local workflow. | Whether export after logout is allowed, what approval state is required, and who may open or export files. |

## Required security contract

Before any database/file operation, identify the actor, role, engagement assignment, record ownership and allowed operation. Enforce at the active main-process boundary. Deny unknown actions and tables as approved. Check indirect relationships, not just supplied engagement IDs. Define bulk-operation behavior and affected-row limits. Return only allowed fields. Log relevant changes without credentials or unnecessary client information.

For evidence and reports, specify draft, prepared, reviewed, approved, locked and reopened states, who can transition them, required reasons, and retained before/after history. A whole-file completion lock needs a separate backend design under T-007; evidence-level flags do not lock every report or trial-balance record.

## Verification limits

The T-003 harness tests the current production main/preload in Electron using synthetic data on Windows x64, Node.js 24.12.0 and npm 11.6.2. It does not exercise packaged installers, untrusted web content/XSS, multiple simultaneous renderer windows, ODBC/Tally, other platforms, real user profiles, restore behavior, or owner UAT. It does not certify that the application is secure. See T-003 in NEXT_TASKS.md and the current evidence in CURRENT_STATUS.md.
